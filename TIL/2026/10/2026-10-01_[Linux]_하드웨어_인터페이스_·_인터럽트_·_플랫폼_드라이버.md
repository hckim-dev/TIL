# 하드웨어 인터페이스와 인터럽트

<a id="notion-3eb1d46c18fc80a1bd5ac093fe31b706"></a>

## 하드웨어 인터페이스

<a id="notion-3eb1d46c18fc80eaafbbeca209718825"></a>

### I/O 포트와 I/O 메모리

모든 주변 장치는 \*\*레지스터(Register)\*\*를 가지고 있다.

주변 장치를 제어한다는 것은 결국 해당 장치의 레지스터를:

- 읽고
- 쓰는 것

을 의미한다.

주변 장치의 레지스터에 접근하려면 \*\*버스 인터페이스(Bus Interface)\*\*가 필요하다.

버스 인터페이스는 다음으로 구성된다.

```text
Address Line
Data Line
Control Line
```

---

<a id="notion-3eb1d46c18fc8079b599faffc08964c9"></a>

### I/O 메모리

일부 CPU는 **하나의 버스 인터페이스**를 이용하여:

```text
Memory
+
Peripheral Device
```

를 모두 접근한다.

이러한 CPU가 주변 장치에 접근하기 위해 사용하는 영역을:

> **I/O Memory**

라고 한다.

즉:

```text
CPU
 ↓
하나의 Bus Interface
 ↓
Memory / Peripheral
```

---

<a id="notion-3eb1d46c18fc8081a0ffe7490909b2cf"></a>

### I/O 포트

일부 CPU는 주변 장치 접근을 위한 **별도의 버스 인터페이스**를 가지고 있다.

이러한 CPU가 주변 장치에 접근하기 위해 사용하는 영역을:

> **I/O Port**

라고 한다.

I/O Port를 사용하는 경우에는 일반 메모리 접근과 별도로 **I/O Port 전용 명령**이 존재하는 경우가 많다.

---

<a id="notion-3eb1d46c18fc80318887e1a9cd942f08"></a>

## I/O Memory / I/O Port 차이

```text
I/O Memory
→ Memory와 Peripheral을 같은 Bus Interface로 접근

I/O Port
→ Peripheral 접근용 Bus Interface가 별도로 존재
```

## 핀 11(PR.04) 레지스터 블록

<a id="notion-3ec1d46c18fc8022b22fc515197ad3a0"></a>

### GPIO Base Physical Address

```text
0x02212880
```

---

<a id="notion-3ec1d46c18fc80258c6df3a7d7d39f2d"></a>

### `GPIO_ENABLE_CONFIG`

Offset:

```text
0x00
```

주요 Bit:

```text
bit 0 → IN_OUT
0: IN
1: OUT

bit 1 → GPIO_ENABLE
0: DISABLE
1: ENABLE
```

즉 LED 출력으로 사용하려면:

```text
IN_OUT = 1
GPIO_ENABLE = 1
```

---

<a id="notion-3ec1d46c18fc8030accfc11aa6a7c162"></a>

### `GPIO_OUTPUT_CONTROL`

Offset:

```text
0x0C
```

```text
bit 0 → GPIO_OUT_CONTROL

0: DRIVEN
1: FLOATED
```

- `OUT`
- `GPIO_ENABLE`
- `DRIVEN`

상태여야 실제 GPIO 출력 가능

---

<a id="notion-3ec1d46c18fc80cbbc15fbb50fe70b3d"></a>

### `GPIO_OUTPUT_VALUE`

Offset:

```text
0x10
```

```text
bit 0 → GPIO_OUTPUT_VALUE

0: LOW
1: HIGH
```

`OUT + ENABLE + DRIVEN` 상태일 때 유효

---

## ⭐ `ioremap()` — ★

GPIO의 물리 주소를 Kernel에서 사용할 가상 주소로 매핑한다.

```text
gpio_base = (unsigned long)ioremap(
    GPIO_PHY_BASE,
    GPIO_PHY_SIZE
);
```

```text
GPIO 물리 주소
0x02212880
      ↓
   ioremap()
      ↓
Kernel 가상 주소
gpio_base
```

실패:

```text
if (gpio_base == 0)
{
    ret = -EIO;
}
```

# LED 초기화

```text
static void led_init(void)
{
    iowrite32(
        ioread32((void *)(gpio_base + GPIO_OUTPUT_VALUE))
        & ~(0x1 << 0),
        (void *)(gpio_base + GPIO_OUTPUT_VALUE)
    );

    iowrite32(
        ioread32((void *)(gpio_base + GPIO_OUTPUT_CONTROL))
        & ~(0x1 << 0),
        (void *)(gpio_base + GPIO_OUTPUT_CONTROL)
    );

    iowrite32(
        (ioread32((void *)(gpio_base + GPIO_ENABLE_CONFIG))
        & ~(0x3 << 0)) | (0x3 << 0),
        (void *)(gpio_base + GPIO_ENABLE_CONFIG)
    );
}
```

설정 내용:

```text
GPIO_OUTPUT_VALUE bit 0
→ 0
→ LED 초기 출력 LOW

GPIO_OUTPUT_CONTROL bit 0
→ 0
→ DRIVEN

GPIO_ENABLE_CONFIG bit 1:0
→ 11
→ GPIO ENABLE + OUTPUT
```

---

<a id="notion-3ec1d46c18fc80db952fdbfe456ff697"></a>

# LED ON

```text
static void led_on(void)
{
    iowrite32(
        ioread32((void *)(gpio_base + GPIO_OUTPUT_VALUE))
        | (0x1 << 0),
        (void *)(gpio_base + GPIO_OUTPUT_VALUE)
    );
}
```

동작:

```text
GPIO_OUTPUT_VALUE bit 0
0 → 1

→ HIGH 출력
→ LED ON
```

---

<a id="notion-3ec1d46c18fc80e6b886f3d719a3def7"></a>

# LED OFF

```text
static void led_off(void)
{
    iowrite32(
        ioread32((void *)(gpio_base + GPIO_OUTPUT_VALUE))
        & ~(0x1 << 0),
        (void *)(gpio_base + GPIO_OUTPUT_VALUE)
    );
}
```

동작:

```text
GPIO_OUTPUT_VALUE bit 0
1 → 0

→ LOW 출력
→ LED OFF
```

# 인터럽트

<a id="notion-3ec1d46c18fc80e8b3def673bbcd1ecc"></a>

## 인터럽트 컨트롤러와 인터럽트 처리

주변 장치에서 발생한 인터럽트는 **인터럽트 컨트롤러**가 수집하여 CPU에 전달한다.

처리 흐름:

```text
실행 중인 코드
↓
IRQ Vector
↓
IRQ Handler
↓
Interrupt Handler
↓
IRQ Handler 복귀
↓
실행 중이던 코드 계속 수행
```

---

<a id="notion-3ec1d46c18fc8087946bdb4591360fe5"></a>

## 프로세스 문맥과 인터럽트 문맥

⭐ **중요 ★**

📝 **시험**

CPU가 Kernel Code를 실행할 때는 크게:

```text
Process Context
또는
Interrupt Context
```

에서 실행된다.

<a id="notion-3ec1d46c18fc805a8325e52465277e71"></a>

### 프로세스 문맥

**Process / Thread와 관련된 Kernel 동작**

대표적인 경우:

- User Process가 System Call을 통해 Kernel에 진입
- User Thread가 System Call을 통해 Kernel에 진입
- Kernel Thread 실행

```text
Process / Thread
↓
Kernel 진입
↓
Process Context
```

---

<a id="notion-3ec1d46c18fc809e9e88f3927699022d"></a>

### 인터럽트 문맥

다음 Handler들은 Interrupt Context에서 실행된다.

- Interrupt Handler
- Kernel Timer Handler
- Tasklet Handler

특징:

- Process Context와 무관
- Interrupt 비활성화 상태에서 수행
- Sleep 불가
- Scheduling 불가
- 가능한 빠르게 처리 후 Return

---

<a id="notion-3ec1d46c18fc80f49868e3d1ee96c307"></a>

## 인터럽트 문맥의 제약사항

<a id="notion-3ec1d46c18fc80f59d26e5a2a04818a2"></a>

### Sleep 불가

Interrupt Context에서는 Sleep할 수 없다.

따라서 다음과 같은 Sleep 가능한 함수 사용 불가:

```text
wait_event()
Semaphore / Mutex
일반 kmalloc()
```

단:

```text
kmalloc(size, GFP_ATOMIC);
```

처럼 `GFP_ATOMIC`을 사용하면 가능.

```text
GFP_KERNEL → Sleep 가능 → Interrupt Context X
GFP_ATOMIC → Sleep X → Interrupt Context O
```

---

<a id="notion-3ec1d46c18fc80568546e4570ae4619d"></a>

### Scheduling 불가

Interrupt Context에서는 Scheduling 불가.

따라서:

```text
schedule();
```

같은 Scheduling 관련 함수 호출 불가.

---

<a id="notion-3ec1d46c18fc80d99176f9fe57cf9257"></a>

### 공유 자원 보호

Interrupt Handler와 공유되는 자원은:

```text
Atomic Variable
Spinlock
```

등으로 보호해야 한다.

---

<a id="notion-3ec1d46c18fc801da966f21093c94d69"></a>

### User Space와 데이터 교환 불가

Interrupt Context에는 User Space가 없으므로:

```text
copy_to_user()
copy_from_user()
```

사용 불가.

---

<a id="notion-3ec1d46c18fc800b8110ea351b7a7a95"></a>

### 빠르게 처리하고 Return

오래 걸리는 작업은 Interrupt Handler에서 직접 처리하지 않고:

```text
thread_fn
Workqueue
```

등으로 넘긴다.

```text
Interrupt Handler
→ 빠른 처리
→ 오래 걸리는 작업은 다른 Context로 넘김
```

## `request_irq()`

## `request_threaded_irq()`

⭐ **중요 ★**

📝 **시험**

`request_irq()`에 <strong>`thread_fn`</strong>**이 추가된 형태**

```text
request_threaded_irq(..., handler, thread_fn, ...);
```

<a id="notion-3ec1d46c18fc80eea2f6f52269e63cc3"></a>

### `handler != NULL`

```text
Interrupt 발생
↓
handler()
↓
IRQ_WAKE_THREAD 반환
↓
thread_fn()
```

- `handler()` → **Interrupt Context**
- `handler()`가 `IRQ_WAKE_THREAD`를 Return하면 `thread_fn()` 호출
- `thread_fn()` → Kernel Thread 함수
- `thread_fn()` → **Process Context**

즉:

```text
handler
→ Interrupt Context

thread_fn
→ Process Context
```

---

<a id="notion-3ec1d46c18fc800da34ce207df446ddb"></a>

### `handler == NULL`

```text
Interrupt 발생
↓
thread_fn()
```

- 직접 작성한 Interrupt Handler 없음
- Interrupt 발생 시 `thread_fn()` 호출
- `thread_fn()` → Kernel Thread 함수
- `thread_fn()` → **Process Context**

즉:

```text
handler == NULL
→ 사용자 Handler 없음
→ thread_fn 실행
→ Process Context
```

---

<a id="notion-3ec1d46c18fc8075b7c1d7c09693d487"></a>

## 📝 `request_threaded_irq()` 시험 핵심

```text
handler != NULL
→ handler 먼저 실행
→ Interrupt Context
→ IRQ_WAKE_THREAD Return
→ thread_fn 실행
→ Process Context
```

```text
handler == NULL
→ handler 없음
→ thread_fn 실행
→ Process Context
```

핵심:

> **handler는 Interrupt Context, thread\_fn은 Process Context**

## 인터럽트 플래그

인터럽트 등록 시 사용하는 Flag는 여러 종류가 있으며 <strong>OR(</strong><strong>`|`</strong><strong>)로 조합 가능</strong>하다.

```text
IRQF_TRIGGER_RISING
IRQF_TRIGGER_FALLING
IRQF_TRIGGER_HIGH
IRQF_TRIGGER_LOW
IRQF_SHARED
```

<a id="notion-3ec1d46c18fc80b6988eda53e54d4bec"></a>

### Trigger Flag

```text
IRQF_TRIGGER_RISING
→ Rising Edge에서 Interrupt 발생

IRQF_TRIGGER_FALLING
→ Falling Edge에서 Interrupt 발생

IRQF_TRIGGER_HIGH
→ High Level에서 Interrupt 발생

IRQF_TRIGGER_LOW
→ Low Level에서 Interrupt 발생
```

<a id="notion-3ec1d46c18fc806d98a6f1faa04c8f0e"></a>

### `IRQF_SHARED`

```text
IRQF_SHARED
→ 하나의 IRQ를 여러 Device가 공유
→ 공유하지 않더라도 사용하는 경우 많음
```

여러 Flag는 다음처럼 함께 사용할 수 있다.

```text
IRQF_TRIGGER_RISING | IRQF_SHARED
```

## Interrupt Handler Return 값

Interrupt Handler는 다음 값을 Return할 수 있다.

<a id="notion-3ec1d46c18fc801c8556d22f9864cbc2"></a>

### `IRQ_NONE`

```text
이 Interrupt를 처리하지 않음
```

<a id="notion-3ec1d46c18fc80a7aefdedf6dbb1136c"></a>

### `IRQ_HANDLED`

```text
Interrupt 처리 완료
```

일반적인 Interrupt Handler에서 정상 처리한 경우:

```text
return IRQ_HANDLED;
```

<a id="notion-3ec1d46c18fc80588a98fdee047d22fd"></a>

### `IRQ_WAKE_THREAD`

```text
thread_fn을 깨움
```

`request_threaded_irq()`에서:

```text
handler()
→ IRQ_WAKE_THREAD Return
→ thread_fn() 실행
```

- `handler()` → Interrupt Context
- `thread_fn()` → Process Context

<a id="notion-3ec1d46c18fc80cfbe49e27e5e471be7"></a>

### `IRQ_RETVAL(x)`

```text
x 값에 따라 IRQ 처리 결과 Return
```

# 인터럽트 공유

하나의 IRQ를 여러 Device가 공유할 수 있다.

```text
device1_open
→ request_irq(..., IRQF_SHARED, ..., &id1);

device2_open
→ request_irq(..., IRQF_SHARED, ..., &id2);
```

조건:

```text
irq_no
→ 동일해야 함

dev_id
→ 서로 달라야 함
```

예:

```text
Device 1
irq_no = 동일
dev_id = &id1

Device 2
irq_no = 동일
dev_id = &id2
```

Interrupt 해제:

```text
free_irq(irq_no, &id1);
free_irq(irq_no, &id2);
```

같은 `irq_no`에 Interrupt가 발생하면:

```text
test1 Handler
+
test2 Handler
```

모두 호출된다.

<a id="notion-3ec1d46c18fc80dc8ef1ec54788881ff"></a>

## `dev_id` 사용 목적

- `free_irq()`에서 어떤 Handler를 해제할지 구분
- Interrupt Handler 내부에서 Device별 데이터를 구분하는 데 사용 가능

# 개별 인터럽트 제어 API


<a id="notion-3ec1d46c18fc80099597e2537855a257"></a>

## Nested 구조

`disable_irq()`는 중첩될 수 있다.

예:

```text
disable_irq()
disable_irq()

→ Disable 2회
```

다시 활성화하려면:

```text

→ Enable도 2회 필요
```

즉:

```text
disable_irq()
↔
enable_irq()
```

를 쌍으로 사용하는 것이 기본이다.

쌍으로 사용하지 않는 경우에는 별도의 Flag를 이용하여 상태를 관리할 수 있다.

## Key Interrupt Handler


- Interrupt 발생할 때마다 1 증가

## Platform Bus, Device, Driver

⭐ **중요 ★**

Platform Bus는 **가상 Bus로 CPU와 주변 장치를 연결**한다.

```text

↓

↓
```

- I2C, SPI 등 다른 Bus 기반 Driver도 비슷한 구조로 동작

## Platform Device 구조체

```text
struct platform_device my_platform_device = {
    .name = DEVICE_NAME,
    .id = 0,
    .num_resources = 0,
    .dev = {
        .release = my_release_device,
    },

```

핵심:

- `.name` → Device 이름
- `.id` → Device 식별 번호
- `.dev` → 내부 `struct device`

```text
.name = DEVICE_NAME
```

이 이름이 Platform Driver의 이름과 Matching된다.

```text
static struct platform_driver my_platform_driver = {
```

- `.probe` → Device와 Driver가 Matching되면 호출

## 플랫폼 Device Resource 활용

Platform Device에서 **Resource와 설정 데이터**를 제공하고, Platform Driver가 이를 읽어서 사용한다.

전체 흐름:

```text
1. 구조체 / 변수 선언
2. Resource 정의
3. 설정 데이터 정의
4. Platform Device 객체 정의
5. Driver에서 Resource / 설정 데이터 획득
6. 획득한 값으로 초기화
```

---

<a id="notion-3ec1d46c18fc80629ee4d0eeb887f4b2"></a>

### Resource / 설정 데이터 관련 구조체

```text
#include <linux/platform_device.h>

#define DEVICE_NAME "my_pdev"

struct my_platform_config
{
    int led_status;
};
```

Driver에서 사용할 값:

```text
static int phy_base;
static int phy_size;
static int irq;
static int irq_flags;
static int led_status;
```

- `phy_base` → I/O Memory 시작 주소
- `phy_size` → I/O Memory 크기
- `irq` → GPIO / IRQ 관련 값
- `irq_flags` → Interrupt Trigger Flag
- `led_status` → LED 초기 상태

---

<a id="notion-3ec1d46c18fc80ddbdb3e025f1d060da"></a>

## Platform Resource 정의

```text
static struct resource my_resources[] = {
    [0] = {
        .start = GPIO_PHY_BASE,
        .end = GPIO_PHY_BASE + GPIO_PHY_SIZE,
        .flags = IORESOURCE_MEM,
    },
    [1] = {
        .start = GPIO_KEY,
        .end = GPIO_KEY,
        .flags = IORESOURCE_IRQ | IRQF_TRIGGER_FALLING,
    },
};
```

<a id="notion-3ec1d46c18fc80b28fe8c1f769b28639"></a>

### Memory Resource

```text
IORESOURCE_MEM
→ I/O Memory Resource
```

- `start` → 시작 주소
- `end` → 끝 주소

<a id="notion-3ec1d46c18fc80ce9065ddd82a20c4c0"></a>

### IRQ Resource

```text
IORESOURCE_IRQ
→ Interrupt Resource
```

```text
IRQF_TRIGGER_FALLING
→ Falling Edge Trigger
```

즉 Platform Device가:

```text
I/O Memory 정보
+
IRQ 정보
```

를 Resource로 제공한다.

---

<a id="notion-3ec1d46c18fc80bc98cdcdaa54ed50ed"></a>

## 설정 데이터 정의

```text
static struct my_platform_config my_config = {
    .led_status = 0,
};
```

Device별 추가 설정값을 별도 구조체로 전달할 수 있다.

여기서는:

```text
led_status = 0
→ LED 초기 상태
```

를 전달한다.

## Platform Device에 Resource 연결

```text
struct platform_device my_platform_device = {
    .name = DEVICE_NAME,
    .id = 0,

    .num_resources = ARRAY_SIZE(my_resources),
    .resource = my_resources,

    .dev = {
        .platform_data = &my_config,
        .release = my_release_device,
    },
};
```

핵심:

```text
.num_resources
→ Resource 개수

.resource
→ Resource 배열

.platform_data
→ Device별 설정 데이터
```

즉:

```text
Platform Device
├─ Resource
│  ├─ I/O Memory
│  └─ IRQ
│
└─ platform_data
   └─ led_status
```

형태로 정보를 Driver에 전달한다.

### I/O Memory Resource

```text
res = platform_get_resource(

    0
```

```text

↓

phy_base / phy_size
```

```text
    0
```

- `irq_flags` → Trigger Flag

# 오늘 배운 내용 요약정리

- **I/O Port / I/O Memory**

  - 주변 장치 Register 접근
  - I/O Memory → `request_mem_region()` / `ioremap()` / `ioread()` / `iowrite()`
  - `ioremap()` → 물리 주소 → Kernel 가상 주소
- **GPIO LED 제어**

  - GPIO Register 설정
  - `led_init()` / `led_on()` / `led_off()`
  - `ioctl()`을 통한 LED ON/OFF
- **Interrupt**

  - Peripheral → Interrupt Controller → CPU → Handler
  - Process Context ↔ Interrupt Context
  - Interrupt Context → Sleep / Scheduling 불가
  - `request_irq()` / `request_threaded_irq()` / `free_irq()`
  - `IRQ_HANDLED`, `IRQ_WAKE_THREAD`
  - `disable_irq()` / `enable_irq()`
  - `local_irq_disable()` / `local_irq_save()`
  - `/proc/interrupts`
- **GPIO Key Interrupt**

  - `gpio_to_irq()`
  - `IRQF_TRIGGER_FALLING`
  - `key_isr()` → `IRQ_HANDLED`
  - IRQ Enable / Disable
- **Device Model**

  - `Bus` / `Device` / `Driver` / `Class`
  - `sysfs` → `/sys`
- **Platform Driver**

  - Platform Bus → CPU와 주변 장치를 연결하는 가상 Bus
  - Device 등록 → Driver 등록 → `name` Matching
  - Matching → `probe()`
  - 제거 → `remove()`
  - Platform Device → Resource / `platform_data` 제공
  - Driver → `platform_get_resource()`로 Resource 획득 후 초기화
