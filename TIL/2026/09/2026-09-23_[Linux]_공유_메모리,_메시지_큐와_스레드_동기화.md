## 공유 메모리(Shared Memory)

프로세스는 각각 **독립적인 가상 주소 공간**을 사용하므로 일반 변수는 서로 공유되지 않는다.

<a id="notion-3e41d46c18fc8081b01eee0fe9b1d09e"></a>

### 📝 시험

```text
부모 프로세스와 자식 프로세스가
일반 변수를 직접 공유할 수 있는가?

→ X
```

`fork()` 직후 변수 값은 같지만 각 프로세스의 주소 공간은 독립적이다.

공유 메모리는 여러 프로세스가 **동일한 메모리 영역을 자신의 주소 공간에 매핑하여 데이터를 공유**할 수 있게 하는 IPC 방식이다.

```text
Process A                  Process B
가상 주소 공간             가상 주소 공간
    │                          │
    └──── Shared Memory ───────┘
```

각 프로세스는 `shmat()`을 통해 공유 메모리를 자신의 가상 주소 공간에 연결한 뒤 일반 메모리처럼 접근한다.

# `shmget()` — 공유 메모리 생성/획득

```text
int shmget(key_t key, size_t size, int shmflg);
```

System V 공유 메모리 세그먼트를 생성하거나 기존 세그먼트를 얻는다.

<a id="notion-3e41d46c18fc800aa441fbf23109997f"></a>

### 매개변수

```text
key
→ 공유 메모리 식별용 Key

size
→ 공유 메모리 크기

shmflg
→ 권한 및 생성 옵션
   IPC_CREAT : 없으면 생성
```

예:

```text
id_shm = shmget(KEY_SHM,
                sizeof(struct shm_buf),
                0666 | IPC_CREAT);
```

<a id="notion-3e41d46c18fc80f989aac26dbf19c6bb"></a>

### 반환값

```text
성공 → Shared Memory ID
실패 → -1
```

<a id="notion-3e41d46c18fc806d8f50ee738b620945"></a>

### ⭐⭐⭐⭐⭐ 매우 중요

`shmget()`은 **공유 메모리 객체/세그먼트를 생성 → 공유 메모리는 물리 메모리에 생성됨**

System V IPC 정보는:

```text
ipcs
```

등으로 확인할 수 있다.

# `shmat()` — 공유 메모리 부착

```text
void *shmat(int shmid,
            const void *shmaddr,
            int shmflg);
```

공유 메모리를 **현재 프로세스의 가상 주소 공간에 연결(attach)** 한다.

<a id="notion-3e41d46c18fc80718952f6bc2ee676ca"></a>

### 매개변수

```text
shmid
→ shmget()으로 얻은 Shared Memory ID

shmaddr
→ 연결할 가상 주소
→ 일반적으로 NULL 사용
→ NULL이면 Kernel이 적절한 주소 선택

shmflg
→ 부착 옵션
```

예:

```text
shmbuf = shmat(id_shm, NULL, 0);
```

성공:

```text
공유 메모리가 연결된 주소 반환
```

실패:

```text
(void *)-1
```

연결 후에는:

```text
shmbuf->status
shmbuf->buf
shmbuf->cs
```

처럼 일반 구조체 포인터처럼 접근할 수 있다.

---

<a id="notion-3e41d46c18fc80628d7dd0b2e44ec390"></a>

# `shmdt()` — 공유 메모리 분리

```text
int shmdt(const void *shmaddr);
```

현재 프로세스의 주소 공간에서 공유 메모리를 **분리(detach)** 한다.

```text
shmdt(shmbuf);
```

<a id="notion-3e41d46c18fc8061bf6cc1bdae7ca9cc"></a>

### 반환값

```text
성공 → 0
실패 → -1
```

<a id="notion-3e41d46c18fc801899c0ec5607755268"></a>

### ⭐⭐⭐ 중요

`shmdt()`는:

```text
프로세스와 공유 메모리 연결만 해제
```

하는 것이다.

즉:

```text
shmdt()
→ 공유 메모리 자체 삭제 X (물리 메모리 상에 그대로 남아 있음)
→ 현재 프로세스의 Mapping만 제거
```

다른 프로세스가 같은 공유 메모리를 계속 사용할 수도 있다.

# `shmctl()` — 공유 메모리 제어

```text
int shmctl(int shmid,
           int cmd,
           struct shmid_ds *buf);
```

공유 메모리의 정보를 확인하거나 삭제 등의 제어를 수행한다.

<a id="notion-3e41d46c18fc8040bf7afb86f9f64927"></a>

### 주요 매개변수

```text
shmid
→ Shared Memory ID

cmd
→ 수행할 명령

buf
→ 정보 입출력용 구조체
```

대표 명령:

```text
IPC_STAT
→ 공유 메모리 정보 획득

IPC_RMID
→ 공유 메모리 삭제 요청 // 중요 ★
```

예:

```text
shmctl(id_shm, IPC_STAT, &dsbuf);
```

→ 크기, 권한 등 정보 확인

```text
shmctl(id_shm, IPC_RMID, NULL);
```

→ 공유 메모리 제거 요청

<a id="notion-3e41d46c18fc80518983e6b139eb4ecd"></a>

### ⚠️ 중요

`IPC_RMID`를 호출했다고 현재 사용 중인 공유 메모리가 즉시 강제로 사라지는 것은 아니다.

```text
IPC_RMID
→ 삭제 대상으로 표시
→ 마지막 attach가 해제되면 실제 제거
```

# 공유 메모리 구조체 예제

```text
struct shm_buf
{
    int status;
    char buf[MAX_BUF];
    unsigned long cs;
};
```

공유 메모리 내부를 구조체 형태로 정의하면 여러 프로세스가 동일한 데이터 구조를 사용할 수 있다.

```text
status
→ 데이터 상태

buf
→ 실제 공유 데이터

cs
→ Checksum
```

---

<a id="notion-3e41d46c18fc800b853fcf669743bcbf"></a>

# `shmput.c` — 공유 메모리 Writer

동작 흐름:

```text
shmget()
   ↓
공유 메모리 획득
   ↓
shmat()
   ↓
현재 프로세스 주소 공간에 부착
   ↓
공유 메모리에 시간 정보 Write
   ↓
Checksum 저장
   ↓
shmdt()
```

핵심:

```text
sprintf(shmbuf->buf, ...);
shmbuf->status = STATUS_VALID;
shmbuf->cs = cs;
```

Writer가 공유 메모리의 구조체를 직접 수정한다.

---

<a id="notion-3e41d46c18fc80d5b7e0d936827882f3"></a>

# `shmget.c` — 공유 메모리 Reader

동작 흐름:

```text
shmget()
   ↓
동일한 공유 메모리 획득
   ↓
shmat()
   ↓
공유 메모리 연결
   ↓
status 확인
   ↓
데이터 및 Checksum 확인
   ↓
shmdt()
```

Writer와 Reader가 같은:

```text
KEY_SHM
```

을 사용하므로 동일한 공유 메모리에 접근할 수 있다.

```text
shmput                  shmget
 Writer                 Reader
   │                       ▲
   │                       │
   └── Shared Memory ──────┘
```

# 공유 메모리의 특징

공유 메모리는 프로세스끼리 데이터를 복사해서 전달하는 방식이 아니라 **동일한 메모리 영역을 함께 접근**하므로 빠른 IPC 방식이다.

하지만 여러 프로세스가 동시에 값을 수정하면:

```text
Race Condition
```

이 발생할 수 있다.

따라서 실제 사용에서는 보통:

```text
Shared Memory
+
Semaphore / Mutex
```

처럼 **데이터 공유 + 동기화**를 함께 사용한다.

예:

```text
Semaphore 획득
     ↓
Shared Memory 접근
     ↓
Semaphore 반환
```

즉 이전에 배운 System V Semaphore와 공유 메모리는 실제로 함께 사용되는 경우가 많다.

<a id="notion-3e41d46c18fc805cabb6f52a531f7dc5"></a>

# 메시지 큐(Message Queue)

메시지 큐는 **프로세스 간 데이터를 메시지 단위로 주고받는 System V IPC 방식**이다.

```text
Process A
   ↓ msgsnd()
[ Kernel Message Queue ]
   ↓ msgrcv()
Process B
```

공유 메모리처럼 같은 메모리를 직접 공유하는 것이 아니라, **커널이 관리하는 메시지 큐에 데이터를 넣고 꺼내는 방식**이다.

---

<a id="notion-3e41d46c18fc8075bc79fe4e27ecf81c"></a>

## 메시지 큐 생성 — `msgget()`

```text
int msgget(key_t key, int msgflg);
```

<a id="notion-3e41d46c18fc8050af9afc5e04d5b324"></a>

### 기능

메시지 큐를 생성하거나 기존 메시지 큐를 얻는다.

<a id="notion-3e41d46c18fc806eb58ed9e5d09f53d2"></a>

### 매개변수

- `key` : 메시지 큐 식별용 key
- `msgflg`

  - 접근 권한
  - `IPC_CREAT` : 없으면 생성

```text
id_msg = msgget((key_t)KEY_MSG, 0666 | IPC_CREAT);
```

<a id="notion-3e41d46c18fc80d99d74fe4b08b2516f"></a>

### 반환값

```text
성공 → 메시지 큐 ID(msqid)
실패 → -1
```

<a id="notion-3e41d46c18fc8058872df55fc356e0c1"></a>

### 기능

# 메시지 보내기 — `msgsnd()`

```text
int msgsnd(int msqid,
           const void *msgp,
           size_t msgsz,
           int msgflg);
```

<a id="notion-3e41d46c18fc803bb0e2ff6cb43cc627"></a>

### 반환값

```text
성공 → 0
실패 → -1
```

---

<a id="notion-3e41d46c18fc80708cc1f2cb2126c296"></a>

## `msgp`

보낼 메시지를 저장한 구조체의 주소.

예:

```text
struct msg_buf
{
    long mtype;
    char mtext[64];
};
```

<a id="notion-3e41d46c18fc807bbce4db743ab7e8a6"></a>

### `mtype`

⚠️ **중요**

- 반드시 구조체의 첫 번째 멤버
- 반드시 `long` 타입
- 반드시 `0`보다 큰 값

```text
long mtype;
```

메시지의 종류를 구분하는 용도로 사용한다.

나머지 데이터 부분은 목적에 맞게 자유롭게 정의할 수 있다.

---

<a id="notion-3e41d46c18fc80cda8bbd24a73105b3f"></a>

## `msgsz`

⚠️ **중요 / 시험 포인트**

`msgsz`에는 <strong>`mtype`</strong>**을 제외한 메시지 데이터 영역의 크기**를 전달한다.

```text
sizeof(struct msg_buf) - sizeof(long)
```

즉:

```text
struct msg_buf
┌──────────────┐
│ long mtype   │ ← msgsz에서 제외
├──────────────┤
│ mtext[64]    │ ← msgsz
└──────────────┘
```

예:

```text
msgsnd(id_msg,
       &msgarr[i],
       sizeof(struct msg_buf) - sizeof(long),
       0);
```

---

<a id="notion-3e41d46c18fc808d98fbeee2405beb49"></a>

## `msgflg`

⚠️ **중요**

기본적으로 큐에 공간이 없으면:

```text
msgsnd()
→ 공간이 생길 때까지 대기(block)
```

하지만:

```text
IPC_NOWAIT
```

를 지정하면:

```text
공간 없음
→ 기다리지 않음
→ 즉시 -1 반환
```

---

<a id="notion-3e41d46c18fc80c78de7cad7734051b8"></a>

# 메시지 받기 — `msgrcv()`

```text
ssize_t msgrcv(int msqid,
               void *msgp,
               size_t msgsz,
               long msgtyp,
               int msgflg);
```

📝 **시험에 잘 나옴**

<a id="notion-3e41d46c18fc80be83b5ceb7704b2d93"></a>

### 반환값

```text
성공 → 실제로 받은 메시지 데이터의 byte 수
실패 → -1
```

---

<a id="notion-3e41d46c18fc803fae21fa00177b2e45"></a>

## `msgp`

`msgsnd()`에서 사용하는 것과 같은 형식의 메시지 구조체 주소.

```text
struct msg_buf msgbuf;
```

---

<a id="notion-3e41d46c18fc80e690adf4c0ed7d46cb"></a>

## `msgsz`

⚠️ **중요**

`msgsnd()`와 동일하게 <strong>`mtype`</strong>**의 크기는 제외한다.**

```text
sizeof(struct msg_buf) - sizeof(long)
```

---

<a id="notion-3e41d46c18fc80239d78d7808873a5ce"></a>

## `msgtyp`

⭐ **시험 포인트 ★★★★**

어떤 `mtype`의 메시지를 받을지 결정한다.

<a id="notion-3e41d46c18fc80bca559d3fff9ac9e51"></a>

### `msgtyp == 0`

```text
큐의 맨 앞 메시지를 받음
mtype 값과 관계없음
```

⚠️ `mtype` 자체는 0이 될 수 없지만, <strong>`msgrcv()`</strong><strong>의</strong> **`msgtyp`** <strong>인자는 0을 사용할 수 있다.</strong>

시험에서 혼동 주의.

---

<a id="notion-3e41d46c18fc8000b5b8fb222e58d617"></a>

### `msgtyp > 0`

```text
mtype == msgtyp
```

인 메시지 중 **가장 먼저 들어온 메시지**를 받는다.

예:

```text
msgrcv(..., 4, ...);
```

→ `mtype == 4`인 첫 번째 메시지 수신

---

<a id="notion-3e41d46c18fc800c9f85d71b7a333f9b"></a>

### `msgtyp < 0`

`|msgtyp|` 이하의 `mtype` 중에서 **가장 작은 mtype을 가진 메시지**를 받는다.

예:

```text
msgtyp = -5
```

큐에:

```text
mtype = 3
mtype = 5
mtype = 2
mtype = 7
```

이 있다면:

```text
5 이하 → 3, 5, 2
그중 가장 작은 mtype → 2
```

따라서 `mtype == 2` 메시지를 받는다.

---

<a id="notion-3e41d46c18fc8010887af7db68905ac1"></a>

## `msgflg`

⚠️ **중요**

원하는 메시지가 없으면 기본적으로:

```text
msgrcv()
→ 원하는 메시지가 들어올 때까지 대기(block)
```

하지만:

```text
IPC_NOWAIT
```

를 사용하면:

```text
원하는 메시지 없음
→ 기다리지 않음
→ 즉시 -1 반환
```

## `msgsnd.c`

여러 개의 메시지를 순서대로 메시지 큐에 넣는다.

```text
struct msg_buf msgarr[] =
{
    {1, "text1"},
    {2, "text2"},
    {3, "text3"},
    ...
};
```

각 메시지는:

```text
msgsnd(id_msg,
       &msgarr[i],
       sizeof(struct msg_buf) - sizeof(long),
       0);
```

으로 전송한다.

⚠️ `msgsz`에서 `mtype`의 `sizeof(long)`을 제외하는 것에 주의.

---

<a id="notion-3e41d46c18fc80e28da2d663fe1d4e60"></a>

## `msgrcv.c`

명령행에서 `msgtyp`을 받아 원하는 메시지를 하나 꺼낸다.

```text
msgrcv(id_msg,
       &msgbuf,
       sizeof(struct msg_buf) - sizeof(long),
       mtype,
       IPC_NOWAIT);
```

예:

```text
./msgrcv 4
```

→ `mtype == 4`인 메시지를 하나 가져온다.

`msgrcv()`로 읽은 메시지는 **큐에서 제거된다.**

---

<a id="notion-3e41d46c18fc808e9b41ff8a827d10ec"></a>

## 📝 시험 핵심

```text
msgsnd / msgrcv의 msgsz
→ mtype(long)의 크기를 제외한다.

mtype
→ 메시지 구조체의 첫 멤버
→ long 타입
→ 0보다 커야 함

msgrcv의 msgtyp
0   → 큐의 첫 번째 메시지
> 0 → 해당 mtype의 첫 번째 메시지 // msgtyp == mtype 중 가만 먼저 들어온 메세지
< 0 → |msgtyp| 이하 중 가장 작은 mtype // 위치(index)가 아니라 값(mtype < msgtyp)을 비교

IPC_NOWAIT
→ 조건이 안 맞아도 기다리지 않고 즉시 실패
```

## 계산기 서버 예제

메시지 큐를 이용하여 **Client가 계산 요청을 보내고, Server가 계산 결과를 다시 돌려주는 구조**이다.

```text
Client
  │
  │ MTYPE_C2S
  │ op1, op2 전송
  ▼
Message Queue
  │
  ▼
Server
  │
  │ 계산 수행
  │ result = op1 * op2
  │
  │ MTYPE_S2C
  ▼
Message Queue
  │
  ▼
Client
  │
  └─ 결과 출력
```

---

<a id="notion-3e41d46c18fc805eaafff35b22d3614e"></a>

### `msg.h`

```text
#define KEY_MSG 0x3331

#define MTYPE_C2S 1 /* Client -> Server */
#define MTYPE_S2C 2 /* Server -> Client */

struct msg_buf
{
    long mtype;
    int op1;
    int op2;
    int result;
};
```

메시지 타입으로 **전송 방향을 구분**한다.

```text
MTYPE_C2S = 1
→ Client → Server 요청

MTYPE_S2C = 2
→ Server → Client 응답
```

메시지에는 두 피연산자와 계산 결과를 저장한다.

---

<a id="notion-3e41d46c18fc809081d5fe648b9cb89a"></a>

## `cal_client.c`

Client는 명령행에서 계산할 두 값을 입력받는다.

```text
./cal_client 10 20
```

<a id="notion-3e41d46c18fc809483c8e9d2e3c5d546"></a>

### 계산 요청 전송

```text
msgbuf.mtype = MTYPE_C2S;
msgbuf.op1 = atoi(argv[1]);
msgbuf.op2 = atoi(argv[2]);
```

메시지 타입을 `MTYPE_C2S`로 지정한 후 Server에게 계산할 값을 전송한다.

```text
msgsnd(id_msg,
       &msgbuf,
       sizeof(struct msg_buf) - sizeof(long),
       0);
```

---

<a id="notion-3e41d46c18fc8039bf0ad6911d5226f8"></a>

### 계산 결과 수신

```text
msgrcv(id_msg,
       &msgbuf,
       sizeof(struct msg_buf) - sizeof(long),
       MTYPE_S2C,
       0);
```

`MTYPE_S2C` 타입의 메시지가 올 때까지 기다린다.

Server가 결과를 보내면:

```text
printf("[%d] %d * %d = %d\n",
       pid,
       msgbuf.op1,
       msgbuf.op2,
       msgbuf.result);
```

으로 결과를 출력한다.

<a id="notion-3e41d46c18fc80f0a55ee6333af002fb"></a>

## `cal_server.c`

Server는 무한 루프를 돌면서 Client의 요청을 계속 기다린다.

```text
for (;;)
{
    ...
}
```

<a id="notion-3e41d46c18fc8046bdb0c7e57df6fbca"></a>

### Client 요청 대기

```text
msgrcv(id_msg,
       &msgbuf,
       sizeof(struct msg_buf) - sizeof(long),
       MTYPE_C2S,
       0);
```

여기서 마지막 `msgflg`가 `0`이므로:

⚠️ **중요**

```text
MTYPE_C2S 메시지가 없음
→ Server는 CPU를 계속 사용하면서 반복하지 않음
→ sleep/block 상태로 대기
→ 메시지가 들어오면 깨어남
```

즉 **busy waiting이 아니다.**

---

<a id="notion-3e41d46c18fc805a88c8e4251b56af86"></a>

### 계산 수행

Client가 보낸 값을 받으면:

```text
msgbuf.result = msgbuf.op1 * msgbuf.op2;
```

계산을 수행한다.

---

<a id="notion-3e41d46c18fc80a6aab0cdd4fd0a6b94"></a>

### 결과 전송

응답 메시지의 타입을:

```text
msgbuf.mtype = MTYPE_S2C;
```

로 변경한다.

그 후:

```text
msgsnd(id_msg,
       &msgbuf,
       sizeof(struct msg_buf) - sizeof(long),
       0);
```

을 통해 결과를 Client에게 보낸다.

<a id="notion-3e41d46c18fc80debe61db90a16af86c"></a>

## 전체 동작 순서

```text
1. Server 실행
   ↓
2. msgrcv(MTYPE_C2S)
   → 요청이 없으므로 대기

3. Client 실행

4. Client
   msgsnd(MTYPE_C2S)
   → op1, op2 전송

5. Server 깨어남
   ↓
   요청 수신
   ↓
   result = op1 * op2

6. Server
   msgsnd(MTYPE_S2C)
   → 결과 전송

7. Client
   msgrcv(MTYPE_S2C)
   → 결과 수신

8. Client 결과 출력 후 종료

9. Server는 다시 다음 요청 대기
```

---

<a id="notion-3e41d46c18fc801aadebc2e3844f2c1c"></a>

## ⚠️ 중요 포인트

```text
MTYPE_C2S
→ Client → Server

MTYPE_S2C
→ Server → Client
```

```text
msgrcv(..., MTYPE_C2S, 0);
```

→ Server는 Client 요청이 없으면 **block 상태로 대기**

```text
msgrcv(..., MTYPE_S2C, 0);
```

→ Client는 Server의 응답이 올 때까지 **block 상태로 대기**

또한 `msgsz`는 이전과 동일하게:

```text
sizeof(struct msg_buf) - sizeof(long)
```

으로 **mtype의 크기를 제외**한다.

이 예제의 핵심은 메시지 큐의 `mtype`을 이용해서:

```text
요청 메시지
응답 메시지
```

를 구분하여 **Client-Server 형태의 통신을 구현하는 것**이다.

# 스레드

<a id="notion-3e41d46c18fc807a9919cc723af7b4ea"></a>

## 스레드 기본

<a id="notion-3e41d46c18fc80c39a1bf4e37eafc26e"></a>

### POSIX 스레드(PThread)

Linux에서는 POSIX 표준의 **POSIX Thread(PThread)** API를 사용할 수 있다.

- \*POSIX(Portable Operating System Interface)\*\*는 운영체제 간 호환성을 위해 정의된 표준 인터페이스이다.

PThread는 하나의 프로세스 안에서 여러 실행 흐름을 만들어 **동시에 작업을 수행할 수 있도록 제공되는 표준 스레드 API**이다.

---

<a id="notion-3e41d46c18fc8069bb50d0bee7fe103c"></a>

## 프로세스, 스레드, 태스크의 관계

스레드는 **프로세스 내부에서 실행되는 흐름의 단위**이다.

기본적으로 하나의 프로세스에는 하나의 기본 스레드가 존재하며, 필요하면 추가 스레드를 생성할 수 있다.

```text
Process
 ├─ Main Thread
 ├─ Thread 1
 └─ Thread 2
```

Linux 커널은 실행 단위를 **태스크(task)** 형태로 관리하며 스레드 단위로 스케줄링한다.

즉, 같은 프로세스에 속한 여러 스레드도 각각 CPU 스케줄링 대상이 될 수 있다.

---

<a id="notion-3e41d46c18fc8098b335dffd0040e39b"></a>

## 스레드의 동작

하나의 프로세스에 속한 스레드들은 프로세스의 자원을 공유한다.

대표적으로 공유되는 자원:

- 코드 영역
- 전역/정적 데이터
- Heap
- 열린 파일 등 프로세스 자원

각 스레드는 자신의 실행 흐름을 유지하기 위해 **자신만의 Stack과 실행 상태**를 가진다.

⚠️ **중요**

스레드끼리 메모리와 자원을 쉽게 공유할 수 있지만, 동시에 같은 자원에 접근하면 Race Condition이 발생할 수 있다.

따라서 공유 자원을 사용하는 경우 **Mutex, Semaphore 등의 동기화 기법이 필요하다.**

---

<a id="notion-3e41d46c18fc80afb422cf03224dc275"></a>

## 스레드의 장단점

📝 **시험에 나올 가능성 있음**

<a id="notion-3e41d46c18fc8095b892c9c58c53834a"></a>

### 장점

- 자원 공유가 쉽다.
- 기다리는 작업 처리가 용이하다.
- 프로세스를 생성하는 것보다 비용이 적게 든다.

<a id="notion-3e41d46c18fc80fe92eaf0841cddcbe9"></a>

### 단점

- 자원을 공유하므로 동시성 문제가 발생하지 않도록 설계해야 한다.
- 문제 발생 시 디버깅이 어려운 편이다.
- 너무 많은 스레드를 생성하여 사용하는 경우 성능 저하가 발생할 수 있다.
- 하나의 스레드라도 문제가 생기면 프로세스 전체에 영향을 미치게 된다.

---

<a id="notion-3e41d46c18fc804cb988ca624f31cd8f"></a>

## 스레드 생성 — `pthread_create()`

```text
int pthread_create(pthread_t *thread,
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *),
                   void *arg);
```

<a id="notion-3e41d46c18fc808a9d1df049f9361c18"></a>

### 기능

새로운 스레드를 생성한다.

<a id="notion-3e41d46c18fc8081b5f3eb97c3bd4cea"></a>

### 매개변수

- `thread`

  - 생성된 스레드의 ID를 저장할 변수의 주소
- `attr`

  - 스레드 속성 지정
  - 별도의 속성이 필요 없으면 `NULL`
- `start_routine`

  - 새 스레드가 실행할 시작 함수
- `arg`

  - `start_routine`에 전달할 인자

<a id="notion-3e41d46c18fc80989132e24f5e63b2bc"></a>

### 반환값

```text
성공 → 0
실패 → 에러 번호
```

PThread 관련 API를 사용할 경우 컴파일 시:

```text
gcc main.c -o main -pthread
```

처럼 `-pthread` 옵션을 추가한다.

---

<a id="notion-3e41d46c18fc80639069ed5f9c1c2d6c"></a>

## 스레드 종료 — `pthread_exit()`

```text
void pthread_exit(void *retval);
```

<a id="notion-3e41d46c18fc80debb15d555cfb3873d"></a>

### 기능

**현재 실행 중인 스레드만 종료**한다.

<a id="notion-3e41d46c18fc80e2a3cff0510714a318"></a>

### 매개변수

- `retval`

  - 종료 결과값
  - 다른 스레드가 `pthread_join()`을 통해 받을 수 있음
  - 필요 없으면 `NULL`

<a id="notion-3e41d46c18fc80dba7fdff2a31e56832"></a>

### 반환값

반환하지 않는다.

```text
pthread_exit(NULL);
```

---

<a id="notion-3e41d46c18fc80598db3c72d4a5881f4"></a>

## 스레드 종료 대기 — `pthread_join()`

```text
int pthread_join(pthread_t thread, void **retval);
```

<a id="notion-3e41d46c18fc80bca1b8d98d16197dbe"></a>

### 기능

지정한 스레드가 종료될 때까지 기다린다.

프로세스의 `wait()`와 비슷하게 **스레드의 종료를 기다리는 역할**을 한다.

<a id="notion-3e41d46c18fc80988c02e70c3cc46b6f"></a>

### 매개변수

- `thread`

  - 종료를 기다릴 스레드 ID
- `retval`

  - 종료한 스레드의 반환값을 받을 주소
  - 필요 없으면 `NULL`

<a id="notion-3e41d46c18fc80bbb0eddfadceef2221"></a>

### 반환값

```text
성공 → 0
실패 → 에러 번호
```

예:

```text
pthread_join(tid, NULL);
```

---

<a id="notion-3e41d46c18fc80f394d9dbf519645d03"></a>

## 스레드 종료 조건

스레드는 다음과 같은 경우 종료될 수 있다.

<a id="notion-3e41d46c18fc801da62efb2c056fdca5"></a>

### 스레드 루틴에서 `pthread_exit()` 호출

```text
pthread_exit(NULL);
```

→ **현재 스레드만 종료**

<a id="notion-3e41d46c18fc8073b76cecb6628c7dba"></a>

### 스레드 시작 함수에서 `return`

```text
void *thread_func(void *arg)
{
    ...
    return NULL;
}
```

→ 해당 스레드 종료

스레드 시작 함수에서 `return`하는 것은 정상적인 스레드 종료 방법이다.

<a id="notion-3e41d46c18fc8009a0bdffea312e4cda"></a>

### 스레드에서 `exit()` 호출

```text
exit(EXIT_SUCCESS);
```

⚠️ `pthread_exit()`과 다르다.

```text
pthread_exit()
→ 현재 스레드만 종료

exit()
→ 프로세스 전체 종료
→ 다른 스레드도 모두 종료
```

<a id="notion-3e41d46c18fc80bbbc3cf925f16984a3"></a>

### 메인 루틴이 종료되는 경우

`main()`에서 `return`하거나 `exit()`하면 **프로세스 전체가 종료되므로 모든 스레드도 함께 종료**된다.

따라서 메인 스레드만 종료하고 다른 스레드를 계속 실행시키고 싶다면 `main()`에서 `pthread_exit()`을 사용할 수 있다.

<a id="notion-3e41d46c18fc80ef9a5ad1abe1d5035e"></a>

### `pthread_cancel()` 호출

다른 스레드에서:

```text
pthread_cancel(thread);
```

을 호출하여 대상 스레드에 취소 요청을 보낼 수 있다.

단, `pthread_cancel()` 호출 즉시 무조건 종료되는 것은 아니며 대상 스레드의 **취소 상태와 취소 지점(cancellation point)** 등에 따라 실제 종료 시점이 결정된다.

<a id="notion-3e41d46c18fc80ad83dcfec57c0a82d1"></a>

## 스레드 구현 예제

하나의 프로세스에서 새로운 스레드를 생성하고, 전역 변수를 공유하며, 메인 스레드가 생성한 스레드의 종료를 기다리는 예제이다.

<a id="notion-3e41d46c18fc8092a740e1571d1b3cd9"></a>

### 스레드 시작 함수

```text
void *thread_func(void *arg)
```

`pthread_create()`에 의해 새 스레드가 시작되면 실행되는 함수이다.

```text
pid_t tid = syscall(__NR_gettid);
```

Linux 커널에서 사용하는 스레드 ID(TID)를 얻는다.

```text
printf("[%d] thread started with arg \"%s\"\n",
       tid, (char *)arg);
```

`pthread_create()`에서 전달한 인자를 `arg`를 통해 받는다.

---

<a id="notion-3e41d46c18fc80f99c2cd7c6423b3c63"></a>

### 전역 변수 공유

```text
int g_count;
```

전역 변수는 같은 프로세스에 속한 스레드들이 공유한다.

스레드 함수에서:

```text
g_count++;
```

를 수행하면 메인 스레드에서도 변경된 `g_count` 값을 확인할 수 있다.

⚠️ **중요**

이 예제에서는 스레드가 하나뿐이라 문제가 잘 드러나지 않지만, 여러 스레드가 동시에:

```text
g_count++;
```

를 수행하면 Race Condition이 발생할 수 있다.

따라서 실제로 여러 스레드가 공유 데이터를 수정한다면 Mutex 등의 동기화가 필요하다.

---

<a id="notion-3e41d46c18fc8016ae4bc2d3e105ca0f"></a>

### 스레드 종료

```text
pthread_exit("Goodbye Thread");
```

현재 스레드를 종료하고 문자열 주소를 종료값으로 전달한다.

이 값은 메인 스레드에서:

```text
pthread_join(thread_id, &thread_ret);
```

를 통해 받을 수 있다.

---

<a id="notion-3e41d46c18fc80beb02cf3662bff5aa7"></a>

### 스레드 생성

```text
ret = pthread_create(&thread_id,
                     NULL,
                     thread_func,
                     "Hello Thread");
```

각 인자의 의미:

```text
&thread_id
→ 생성된 스레드 ID 저장

NULL
→ 기본 스레드 속성 사용

thread_func
→ 스레드가 실행할 시작 함수

"Hello Thread"
→ thread_func()에 전달할 인자
```

새로 생성된 스레드는:

```text
thread_func("Hello Thread");
```

와 같은 형태로 실행된다고 이해하면 된다.

---

<a id="notion-3e41d46c18fc80269c56d3c78c728b2e"></a>

### 스레드 종료 대기

```text
ret = pthread_join(thread_id, &thread_ret);
```

메인 스레드는 `thread_id` 스레드가 종료될 때까지 기다린다.

스레드에서:

```text
pthread_exit("Goodbye Thread");
```

를 호출하면:

```text
thread_ret
```

에 `"Goodbye Thread"`의 주소가 전달된다.

이후:

```text
printf("[%d] thread returned \"%s\" (g_count = %d)\n",
       pid, (char *)thread_ret, g_count);
```

를 통해 스레드의 종료값과 공유된 전역 변수의 최종값을 확인한다.

---

<a id="notion-3e41d46c18fc807a9747e0c2548b445f"></a>

### 전체 동작 순서

```text
Main Thread
   ↓
pthread_create()
   ↓
새 Thread 생성
   ↓
thread_func() 실행
   ↓
g_count 증가
   ↓
pthread_exit()
   ↓
Thread 종료

Main Thread
   ↓
pthread_join()
   ↓
Thread 종료까지 대기
   ↓
thread_ret 획득
   ↓
g_count 최종값 출력
```

이 예제의 핵심은:

```text
pthread_create()
→ 스레드 생성

전역 변수
→ 스레드 간 공유

pthread_exit()
→ 현재 스레드 종료 + 종료값 전달

pthread_join()
→ 특정 스레드 종료 대기 + 종료값 획득
```

이다.

<a id="notion-3e41d46c18fc80b0b32cfa58b4c2640a"></a>

## 스레드 동기화

<a id="notion-3e41d46c18fc80f49e67f65c829c6e07"></a>

### 뮤텍스(Mutex)

뮤텍스를 이용하면 **상호 배제(Mutual Exclusion) 구간**을 만들 수 있다.

상호 배제 구간은 \*\*한 번에 하나의 스레드만 진입할 수 있는 임계 영역(Critical Section)\*\*을 의미한다.

이미 다른 스레드가 뮤텍스를 획득한 상태라면, 다른 스레드는 뮤텍스를 얻을 수 있을 때까지 대기한다.

```text
Thread 1
pthread_mutex_lock()
        ↓
   [ 임계 영역 ]
        ↓
pthread_mutex_unlock()

Thread 2
pthread_mutex_lock()
        ↓
Thread 1이 unlock할 때까지 대기
```

⚠️ **중요**

여러 스레드가 같은 공유 자원을 동시에 수정하면 Race Condition이 발생할 수 있으므로, 공유 자원을 사용하는 임계 영역을 뮤텍스로 보호해야 한다.

---

<a id="notion-3e41d46c18fc80bca9e2eef5f475e664"></a>

### 뮤텍스 관련 함수

<a id="notion-3e41d46c18fc80b083e8eaf635eb1b64"></a>

#### `pthread_mutex_init()`

```text
int pthread_mutex_init(pthread_mutex_t *mutex,
                       const pthread_mutexattr_t *attr);
```

뮤텍스를 초기화한다.

```text
pthread_mutex_init(&g_mutex, NULL);
```

- `mutex` : 초기화할 뮤텍스
- `attr` : 뮤텍스 속성, 기본 속성 사용 시 `NULL`
- 성공 → `0`
- 실패 → 에러 번호

---

<a id="notion-3e41d46c18fc8052bde6f8faff89e95d"></a>

#### `pthread_mutex_lock()`

```text
int pthread_mutex_lock(pthread_mutex_t *mutex);
```

뮤텍스를 획득한다.

```text
pthread_mutex_lock(&g_mutex);
```

다른 스레드가 이미 획득한 상태라면 해당 뮤텍스를 사용할 수 있을 때까지 대기한다.

---

<a id="notion-3e41d46c18fc805a9889ca771225387c"></a>

#### `pthread_mutex_unlock()`

```text
int pthread_mutex_unlock(pthread_mutex_t *mutex);
```

현재 획득한 뮤텍스를 반납한다.

```text
pthread_mutex_unlock(&g_mutex);
```

뮤텍스를 반납하면 기다리던 다른 스레드가 임계 영역에 진입할 수 있다.

---

<a id="notion-3e41d46c18fc80af993dfeceaa5ade8e"></a>

#### `pthread_mutex_destroy()`

```text
int pthread_mutex_destroy(pthread_mutex_t *mutex);
```

더 이상 사용하지 않는 뮤텍스를 제거한다.

```text
pthread_mutex_destroy(&g_mutex);
```

---

<a id="notion-3e41d46c18fc802ba035e35f61b6961b"></a>

## 여러 개의 스레드에 뮤텍스 적용

두 개의 스레드가 하나의 전역 변수 `g_count`를 동시에 증가시키는 예제이다.

```text
int g_count;
pthread_mutex_t g_mutex;
```

`g_count`는 두 스레드가 함께 사용하는 **공유 자원**이다.

---

<a id="notion-3e41d46c18fc80688ea1d2fc35d772ce"></a>

### 임계 영역

두 스레드 모두 다음 코드를 반복한다.

```text
pthread_mutex_lock(&g_mutex);

// 임계 영역
temp = g_count;
usleep(1);
g_count = ++temp;
count++;

pthread_mutex_unlock(&g_mutex);
```

공유 변수 `g_count`를 읽고 수정하는 구간을 뮤텍스로 보호한다.

```text
lock
 ↓
g_count 읽기
 ↓
값 증가
 ↓
g_count에 저장
 ↓
unlock
```

따라서 한 스레드가 이 작업을 수행하는 동안 다른 스레드는 동일한 임계 영역에 들어갈 수 없다.

---

<a id="notion-3e41d46c18fc8043a2d8fa1617232128"></a>

### 왜 뮤텍스가 필요한가?

뮤텍스가 없다면 두 스레드가 동시에 다음과 같이 실행될 수 있다.

```text
초기 g_count = 10

Thread 1              Thread 2
temp = 10             temp = 10
temp++                 temp++
g_count = 11          g_count = 11
```

두 스레드가 각각 한 번씩 증가시켰으므로 기대값은 `12`지만 실제 결과는 `11`이 될 수 있다.

이것이 **Race Condition**이다.

뮤텍스를 적용하면:

```text
Thread 1
lock
10 → 11
unlock

Thread 2
lock
11 → 12
unlock
```

순서로 처리되므로 값이 정상적으로 증가한다.

---

<a id="notion-3e41d46c18fc80a5a0e4ecdeb76d1d63"></a>

### `usleep(1)`의 의미

```text
temp = g_count;
usleep(1);
g_count = ++temp;
```

`g_count`를 읽은 후 잠시 대기하도록 만들어 **Race Condition이 발생할 가능성을 쉽게 관찰하기 위한 코드**이다.

하지만 이 구간 전체가 뮤텍스로 보호되어 있으므로 다른 스레드는 중간에 접근할 수 없다.

---

<a id="notion-3e41d46c18fc80cebf45c0e98712d47f"></a>

### 스레드 생성

```text
int n = 10000;

pthread_create(&thread_id1, NULL, thread_func1, &n);
pthread_create(&thread_id2, NULL, thread_func2, &n);
```

두 스레드 모두 같은 `n`의 주소를 전달받아 각각 `10000`번 반복한다.

각 스레드는:

```text
*(int *)arg
```

를 통해 전달된 값을 읽는다.

---

<a id="notion-3e41d46c18fc80628e5ddc1541b7ef03"></a>

### 스레드 종료 대기

```text
pthread_join(thread_id1, NULL);
pthread_join(thread_id2, NULL);
```

메인 스레드는 두 스레드가 모두 종료될 때까지 기다린다.

두 스레드가 각각 `10000`번씩 정상적으로 증가시켰다면 최종적으로:

```text
g_count = 20000
```

이 된다.

---

<a id="notion-3e41d46c18fc80e1b978ebd8e4c19905"></a>

### 뮤텍스 제거

모든 스레드가 종료된 후:

```text
pthread_mutex_destroy(&g_mutex);
```

를 호출하여 뮤텍스를 제거한다.

전체 흐름은:

```text
pthread_mutex_init()
        ↓
Thread 1, Thread 2 생성
        ↓
pthread_mutex_lock()
        ↓
공유 자원 접근
        ↓
pthread_mutex_unlock()
        ↓
pthread_join()
        ↓
pthread_mutex_destroy()
```

이다.

<a id="notion-3e41d46c18fc805fa626e3b0a7e472a7"></a>

## 오늘 배운 내용 요약

<a id="notion-3e41d46c18fc80b1a954f63ca4a18210"></a>

### 공유 메모리

- 프로세스는 서로 독립된 가상 주소 공간을 사용하므로 **일반 변수는 직접 공유할 수 없다.**
- `shmget()` : 공유 메모리 생성/획득
- `shmat()` : 공유 메모리를 현재 프로세스에 연결
- `shmdt()` : 연결만 해제
- `shmctl(..., IPC_RMID, ...)` : 공유 메모리 삭제 요청
- 공유 메모리는 여러 프로세스가 같은 데이터를 직접 접근하므로 빠르지만 **Race Condition 방지를 위한 동기화가 필요**하다.  

**키워드:** `shmget → shmat → 접근 → shmdt → IPC_RMID`

---

<a id="notion-3e41d46c18fc808fb89dff90e2e321b9"></a>

### 메시지 큐

- 커널이 관리하는 큐를 통해 프로세스끼리 **메시지 단위로 데이터 전달**
- `msgget()` : 메시지 큐 생성/획득
- `msgsnd()` : 메시지 전송
- `msgrcv()` : 메시지 수신
- `msgctl()` : 정보 확인 / 제거
- `mtype`은 `long`, 0보다 커야 함.
- `msgsz`는 **mtype 크기를 제외한 크기**
- `IPC_NOWAIT`이 없으면 조건이 만족될 때까지 block될 수 있음.  

⭐ <strong>시험 중요 —</strong> <strong>`msgrcv()`</strong><strong>의</strong> **`msgtyp`**

```text
msgtyp == 0  → 큐의 첫 번째 메시지
msgtyp > 0   → mtype == msgtyp인 첫 메시지
msgtyp < 0   → |msgtyp| 이하 중 가장 작은 mtype
```

`mtype`은 0이 될 수 없지만 <strong>`msgtyp`</strong>**에는 0을 줄 수 있음**에 주의. 

계산기 서버 예제에서는:

```text
Client -- MTYPE_C2S --> Server
Client <-- MTYPE_S2C -- Server
```

처럼 `mtype`을 이용해 **요청/응답 방향을 구분**했다. 

---

<a id="notion-3e41d46c18fc80df9890deb0c7723922"></a>

### 스레드

- 스레드 = **프로세스 내부의 실행 흐름**
- 하나의 프로세스 안에 여러 스레드 생성 가능
- 스레드는 코드, 전역/정적 데이터, Heap, 파일 등의 프로세스 자원을 공유
- 각 스레드는 자신의 Stack과 실행 상태를 가짐.
- 자원을 공유하기 때문에 **동기화가 중요**하다. 

핵심 PThread API:

```text
pthread_create() → 스레드 생성
pthread_exit()   → 현재 스레드 종료
pthread_join()   → 특정 스레드 종료 대기
pthread_cancel() → 스레드 취소 요청
```

컴파일:

```text
gcc main.c -o main -pthread
```

`pthread_exit()`은 **현재 스레드만 종료**, `exit()`은 **프로세스 전체 종료**라는 차이를 기억.  

---

<a id="notion-3e41d46c18fc800c8d99d766b5a5da2d"></a>

### 스레드 동기화 — Mutex

여러 스레드가 같은 공유 데이터를 동시에 수정하면 **Race Condition**이 발생할 수 있다.

뮤텍스는 한 번에 하나의 스레드만 임계 영역에 들어가도록 하는 **상호 배제** 도구다. 

```text
pthread_mutex_init()
        ↓
pthread_mutex_lock()
        ↓
    임계 영역
        ↓
pthread_mutex_unlock()
        ↓
pthread_mutex_destroy()
```

예제에서는 두 스레드가 `g_count`를 각각 10,000번 증가시키며, 뮤텍스로 보호하면 최종적으로:

```text
g_count = 20000
```

이 되도록 보장한다. 뮤텍스가 없다면 두 스레드가 같은 값을 읽고 덮어써서 증가 횟수가 손실될 수 있다. 

<a id="notion-3e41d46c18fc800da57edc27fd0ffd33"></a>

### 오늘 핵심 연결

```text
프로세스 간 데이터 공유
→ Shared Memory / Message Queue

Shared Memory
→ 직접 같은 데이터 접근
→ 빠르지만 동기화 필요

Message Queue
→ 커널 큐를 통한 메시지 전달

프로세스 내부 병렬 실행
→ Thread

Thread 간 공유 자원 보호
→ Mutex
```

<strong>시험 쪽에서는</strong> <strong>`shmdt vs IPC_RMID`</strong><strong>,</strong> <strong>`msgsz`</strong><strong>,</strong> <strong>`msgrcv msgtyp`</strong><strong>,</strong> <strong>`pthread_exit vs exit`</strong><strong>, Mutex와 Race Condition을 우선 기억하면 된다.</strong>
