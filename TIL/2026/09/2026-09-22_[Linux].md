# `fork()` \+ `exec()` 구현

`fork()`로 **자식 프로세스를 생성한 뒤**, 자식에서 `exec()`를 호출해 **원하는 프로그램으로 교체**하는 방식이다.

```text
Parent
  │
  ├─ fork()
  │    ├─ Parent → wait()
  │    └─ Child  → exec()
  │                   ↓
  │              다른 프로그램 실행
  │
  └─ 자식 종료 후 계속 실행
```

예를 들어 자식 PID가 `1001`이라면:

```text
fork() 직후 자식 PID = 1001
        ↓
execlp("ls", ...)
        ↓
ls 프로그램으로 교체
        ↓
PID = 1001 그대로 유지
```

`exec()`는 **새 프로세스를 만드는 것이 아니라 현재 프로세스의 실행 이미지를 교체**하므로 PID가 바뀌지 않는다.

<a id="notion-3e31d46c18fc8042b0c4c06e511a3a65"></a>

### 왜 `fork()` 후 `exec()`를 사용하는가?

부모 프로그램은 계속 실행하면서 자식에게 다른 프로그램을 실행시킬 수 있다.

```text
Parent → 기존 작업 계속
Child  → exec()로 다른 프로그램 실행
```

**장점**

- 부모와 자식을 독립적으로 실행 가능
- 여러 작업을 병행할 수 있음
- 프로그램 역할을 프로세스별로 분리하여 구조가 단순해질 수 있음
- Shell이나 서버 프로그램에서 많이 사용하는 기본 구조

**단점**

- 프로세스가 추가되므로 메모리, PID, 스케줄링 등의 자원 사용
- 여러 프로세스가 동시에 실행되므로 동기화와 종료 관리가 필요
- Thread보다 프로세스 생성/전환 비용이 상대적으로 큼

---

<a id="notion-3e31d46c18fc8062bce0cd52455b3d11"></a>

## 📝 시험 — `fork()` \+ `exec()`의 종료 상태

자식에서:

```text
ret = execlp("ls", "ls", "-l", NULL);
```

`exec()`가 성공하면 현재 자식 프로세스가 `ls`로 교체되므로 **그 아래 코드는 실행되지 않는다.**

```text
printf("[%d] ret = %d\n", pid, ret);
return EXIT_FAILURE;
```

이 코드는 <strong>`exec()`</strong>**가 실패했을 때만 실행**된다.

<a id="notion-3e31d46c18fc80738e5ce883daa88dcf"></a>

### 예시

정상 실행:

```text
execlp("ls", "ls", "-l", NULL);
```

`ls`가 정상 종료하면:

```text
exit code = 0
status = 0x0000
```

존재하지 않는 파일 등을 `ls`에 전달하여 `ls` 자체가 오류로 종료하면 환경에 따라:

```text
exit code = 2
status = 0x0200
```

등이 될 수 있다.

실행할 프로그램 자체를 찾지 못하면:

```text
ret = execlp("xxx", "xxx", "-l", NULL);
```

`execlp()`가 `-1`을 반환하고 다음 코드가 실행된다.

```text
return EXIT_FAILURE;   // 1
```

따라서 부모가 `wait()`로 받은 정상 종료 status는:

```text
0x0100
```

<a id="notion-3e31d46c18fc80849c98e947c637413c"></a>

### ⭐ 시험 포인트

```text
return 1 → status 0x0100
return 2 → status 0x0200
return 8 → status 0x0800
```

`fork()` → `exec()` → `wait()`의 실행 흐름과 **최종 status 값 추적**을 할 수 있어야 한다.

# 시그널(Signal)

시그널은 **프로세스에게 특정 사건이 발생했음을 알리는 비동기적인 신호**이다.

대표 예:

```text
Ctrl + C  → SIGINT  (2)
Ctrl + \  → SIGQUIT (3)
```

---

<a id="notion-3e31d46c18fc80caa724de385012c70e"></a>

## 시그널의 기본 동작

| 동작 | 의미 |
| --- | --- |
| `Term` | 프로세스 종료 |
| `Core` | Core dump 생성 후 종료 |
| `Stop` | 프로세스 정지 |
| `Cont` | 정지된 프로세스 재개 |
| `Ign` | 시그널 무시 |

`SIG_DFL`

→ 해당 시그널의 **기본 동작 수행**

`SIG_IGN`

→ 해당 시그널을 **무시**

<a id="notion-3e31d46c18fc80118a37d8e57a3bde30"></a>

### ⚠️ 중요

```text
SIGKILL
SIGSTOP
```

은 **catch하거나 ignore할 수 없다.**

즉 사용자 정의 handler로 바꾸거나 무시할 수 없다.

---

<a id="notion-3e31d46c18fc808ba162fd882765822f"></a>

# `signal()`

```text
sighandler_t signal(int signum, sighandler_t handler);
```

특정 시그널이 발생했을 때 실행할 동작을 설정한다.

<a id="notion-3e31d46c18fc8009a997dc76899fc84b"></a>

### 매개변수

```text
signum
→ 설정할 시그널 번호

handler
→ 실행할 시그널 핸들러
→ SIG_DFL : 기본 동작
→ SIG_IGN : 무시
```

<a id="notion-3e31d46c18fc80c1a4f1f1d3cf30f11f"></a>

### 반환값

성공:

```text
이전에 설정되어 있던 signal handler 반환
```

실패:

```text
SIG_ERR
```

예:

```text
signal(SIGINT, sigint_handler);
```

→ `Ctrl+C`로 `SIGINT`가 발생하면 `sigint_handler()`가 실행된다.

---

<a id="notion-3e31d46c18fc80d68993dbf3b00c5611"></a>

## 시그널 핸들러

```text
void sigint_handler(int signal)
{
    ...
}
```

handler의 매개변수에는 **발생한 시그널 번호**가 전달된다.

시그널 handler는 프로그램의 정상 실행 중간에 갑자기 호출될 수 있으므로 사용할 수 있는 함수에 제한이 있다.

<a id="notion-3e31d46c18fc80b5bd3ceb783b1b5a61"></a>

### Async-signal-safe

시그널 handler 내부에서도 안전하게 사용할 수 있도록 POSIX에서 보장된 함수를 **Async-signal-safe 함수**라고 한다.

대표적으로:

```text
read()
write()
open()
close()
```

등이 있다.

반면:

```text
printf()
```

는 일반적으로 **Async-signal-safe가 아니다.**

> 수업 예제에서는 확인 목적으로 `printf()`를 사용하지만 실제 안정적인 signal handler에서는 주의해야 한다.

실무에서는 `signal()`보다 동작을 세밀하게 지정할 수 있는 `sigaction()`을 주로 사용한다.

---

<a id="notion-3e31d46c18fc80fa8620c0e08069e8fa"></a>

# 시그널 핸들러 예제 동작

```text
signal(SIGINT, sigint_handler);
```

설정 후:

```text
프로그램 실행
   ↓
sleep(1)
   ↓
Ctrl+C
   ↓
SIGINT 발생
   ↓
sigint_handler() 실행
   ↓
기존 실행 흐름으로 복귀
```

`SIG_DFL`로 설정하면 `Ctrl+C`의 기본 동작인 **프로세스 종료**가 수행된다.

```text
signal(SIGINT, SIG_DFL);
```

`SIG_IGN`이면 무시한다.

```text
signal(SIGINT, SIG_IGN);
```

# 시그널 전송

<a id="notion-3e31d46c18fc8091b5bacec20b8a1019"></a>

## `kill` 명령

이름과 달리 반드시 프로세스를 종료하는 명령은 아니며, **프로세스에 시그널을 전송하는 명령**이다.

```text
kill -10 1234
```

→ PID `1234`에 signal `10` 전송

```text
kill 1003 1005 2004
```

signal 번호를 생략하면 기본적으로:

```text
SIGTERM(15)
```

을 전송한다.

```text
kill -l
```

→ signal 목록 확인

```text
kill -l 2
```

→ signal 2의 이름 확인

---

<a id="notion-3e31d46c18fc80859103e0341dc99d24"></a>

# `kill()` 함수

```text
int kill(pid_t pid, int sig);
```

프로세스에 시그널을 전송한다.

<a id="notion-3e31d46c18fc800a816dee17eb71ae73"></a>

### 매개변수

```text
pid
→ 시그널을 받을 프로세스 지정

sig
→ 전송할 시그널 번호
```

<a id="notion-3e31d46c18fc8086a76ec9640c32d199"></a>

### 반환값

```text
성공 → 0
실패 → -1, errno 설정
```

---

<a id="notion-3e31d46c18fc80d2847ec3a4841f3d39"></a>

## ⚠️ 중요 — `sig == 0`

```text
kill(pid, 0);
```

signal 0이라는 실제 시그널을 보내는 것이 아니다.

```text
sig = 0
→ 실제 signal 전송 X
→ 해당 PID가 존재하고 접근 권한이 있는지 검사
```

따라서 프로세스 존재 여부 등을 확인할 때 사용할 수 있다.

---

<a id="notion-3e31d46c18fc8022a53adcc74f975dee"></a>

# 시그널 송수신 예제

`send.c`

```text
PID와 signal 번호 입력
       ↓
kill(pid, signal)
       ↓
대상 프로세스에 signal 전송
```

`signal.c`

```text
SIGINT  → sigint_handler()
SIGUSR1 → sigusr1_handler()
```

실행 흐름:

```text
signal.c 실행
    ↓
signal handler 등록
    ↓
대기 중
    ↓
send.c에서 kill() 호출
    ↓
signal 전달
    ↓
등록된 handler 실행
```

즉 <strong>한 프로세스가</strong> <strong>`kill()`</strong>**로 시그널을 보내고 다른 프로세스가 handler를 통해 받아 처리**하는 구조이다.

# 프로세스 간 통신(IPC)

프로세스는 서로 독립적인 주소 공간을 사용하므로 일반 변수만으로 데이터를 직접 공유할 수 없다.

따라서 프로세스 간 데이터를 전달하기 위한 **IPC(Inter-Process Communication)** 방법이 필요하다.

---

<a id="notion-3e31d46c18fc80de9e06edb1b253e9a1"></a>

# 파이프(Pipe)

파이프는 프로세스와 프로세스 사이에 데이터를 전달하는 **통신 통로**이다.

기본적인 pipe는 단방향이다.

```text
Process A                Process B
   │                        ▲
   │ Write                  │ Read
   └──────── Pipe ──────────┘
```

한쪽 끝은 쓰기, 다른 한쪽 끝은 읽기에 사용한다.

---

<a id="notion-3e31d46c18fc80cf8b6ad4b70e3677c8"></a>

## 파이프 종류

- **프로세스 파이프**: `popen()`, `pclose()`
- **이름 없는 파이프**: `pipe()`
- **이름 있는 파이프**: FIFO

---

<a id="notion-3e31d46c18fc80fcb090c2ff0629a70a"></a>

# 프로세스 파이프 `popen()`

```text
FILE *popen(const char *command, const char *type);
```

명령을 실행하고 그 프로세스와 **단방향 pipe를 연결**한다.

<a id="notion-3e31d46c18fc806688d8e59d2e5b5cea"></a>

### `type`

```text
"r"
→ 실행한 command의 stdout을 읽음

"w"
→ 실행한 command의 stdin에 데이터를 씀
```

성공:

```text
FILE * 반환
```

실패:

```text
NULL
```

`popen()`은 내부적으로 shell을 통해 command를 실행한다.

---

<a id="notion-3e31d46c18fc808bb18be9c5bd4cc72a"></a>

# `pclose()`

```text
int pclose(FILE *stream);
```

`popen()`으로 생성한 pipe를 닫고 **실행한 프로세스가 종료될 때까지 기다린다.**

반환값은 해당 command의 **종료 상태**와 관련된 값이다.

---

<a id="notion-3e31d46c18fc80a3be39dff5d8d7f95e"></a>

# 쓰기 전용 프로세스 파이프

```text
fp_w = popen("tr a-z A-Z", "w");
```

현재 프로그램에서 `tr` 프로세스의 **표준 입력(stdin)** 으로 데이터를 전달한다.

```text
현재 Process
     │
   fwrite()
     │
     ▼
   Pipe
     │
     ▼
tr 프로세스 stdin
     │
     ▼
소문자 → 대문자 변환
```

```text
pclose(fp_w);
```

→ pipe를 닫고 `tr` 프로세스가 종료되기를 기다린다.

---

<a id="notion-3e31d46c18fc80b7a3ccf7b7a6fcb4e6"></a>

# 읽기 전용 프로세스 파이프

```text
fp_r = popen(cmd, "r");
```

예:

```text
popen("ls /home", "r");
```

실행한 명령의 **표준 출력(stdout)** 을 pipe를 통해 읽을 수 있다.

```text
ls 프로세스
    │
 stdout
    │
    ▼
   Pipe
    │
  fread()
    ▼
현재 Process
```

따라서:

```text
fread(buf, 1, BUF_SIZE - 1, fp_r);
```

로 `ls` 출력 결과를 읽고 화면에 출력한다.

```text
pclose(fp_r);
```

→ pipe를 닫고 `ls` 프로세스의 종료까지 기다린다.

<a id="notion-3e31d46c18fc80ef8851eb5ea1413fb5"></a>

# 📝 시험 — `popen()` 빈칸 채우기

코드가 주어지고 다음 형태의 `popen()`을 완성하는 문제가 나올 가능성이 높다.

```text
popen("명령어", "r 또는 w");
```

핵심은 **현재 프로세스 기준으로 읽는지/쓰는지** 판단하는 것이다.

<a id="notion-3e31d46c18fc8039b002ec258d008b61"></a>

### 쓰기 전용 프로세스 파이프

현재 프로그램이 실행한 명령의 **stdin으로 데이터를 보낼 때**:

```text
fp_w = popen("tr a-z A-Z", "w");
```

```text
현재 프로세스
    │
    │ fwrite()
    ▼
Pipe
    │
    ▼
tr의 stdin
```

따라서:

```text
현재 프로그램이 command에게 쓴다
→ "w"
```

<a id="notion-3e31d46c18fc80e8bb36f6d073672da3"></a>

### 읽기 전용 프로세스 파이프

실행한 명령의 **stdout 결과를 현재 프로그램이 읽을 때**:

```text
fp_r = popen("ls /etc", "r");
```

```text
ls의 stdout
    │
    ▼
Pipe
    │
    │ fread()
    ▼
현재 프로세스
```

따라서:

```text
현재 프로그램이 command의 결과를 읽는다
→ "r"
```

<a id="notion-3e31d46c18fc807c9104e6c2f9f9add9"></a>

### ⭐ 시험에서 판단하는 방법

코드에서 다음 함수를 보면 빠르게 판단할 수 있다.

```text
fwrite(..., fp);
```

→ 현재 프로그램이 pipe에 데이터를 씀

```text
popen("명령어", "w");
```

반대로:

<br>

```text
fread(..., fp);
```

→ 현재 프로그램이 pipe에서 데이터를 읽음

```text
popen("명령어", "r");
```

예상 문제:

```text
fp = popen("tr a-z A-Z", ___);
fwrite(str, 1, len, fp);
```

정답:

```text
"w"
```

```text
fp = popen("ls /etc", ___);
fread(buf, 1, sizeof(buf), fp);
```

정답:

```text
"r"
```

> <strong>`r/w`</strong><strong>는 실행되는 command 기준이 아니라</strong> <strong>`popen()`</strong>**을 호출한 현재 프로세스 기준으로 생각하면 된다.**

<a id="notion-3e31d46c18fc8064b56fe013402afe3c"></a>

# 이름 없는 파이프(Anonymous Pipe)

파이프는 프로세스 사이에서 데이터를 전달하기 위한 **단방향 IPC 통로**이다.

```text
int pipe(int pipefd[2]);
```

성공:

```text
0
```

실패:

```text
-1
errno 설정
```

`pipe()`를 호출하면 두 개의 File Descriptor가 생성된다.

```text
fd_pipe[0] → 읽기 끝(Read End)
fd_pipe[1] → 쓰기 끝(Write End)
```

구조:

```text
write(fd_pipe[1])
        │
        ▼
      Pipe
        │
        ▼
read(fd_pipe[0])
```

---

<a id="notion-3e31d46c18fc801784cfc39254486b6e"></a>

## `pipe2()`

```text
int pipe2(int pipefd[2], int flags);
```

`pipe()`와 같은 역할을 하지만 생성과 동시에 추가 flag를 지정할 수 있다.

대표적으로:

```text
O_NONBLOCK
→ Non-blocking pipe

O_CLOEXEC
→ exec() 실행 시 FD 자동 close
```

---

<a id="notion-3e31d46c18fc807cbd42fdf7cfb24442"></a>

# 간단한 파이프 구현

```text
pipe(fd_pipe);
```

파이프 생성 후:

```text
write(fd_pipe[1], wbuf, ...);
```

→ 쓰기 끝에 데이터 저장

```text
read(fd_pipe[0], rbuf, ...);
```

→ 읽기 끝에서 데이터 읽기

예제에서는 같은 프로세스가 직접 쓰고 읽지만, 실제 파이프의 주요 용도는 **프로세스 간 통신**이다.

---

<a id="notion-3e31d46c18fc80a39136f922a6772f1f"></a>

# 파이프로 부모-자식 통신

보통 `fork()` **전에** 파이프를 생성한다.

```text
pipe()
  ↓
fork()
```

`fork()` 시 File Descriptor 정보도 자식에게 복제되므로 부모와 자식 모두:

```text
fd_pipe[0]
fd_pipe[1]
```

을 가지게 된다.

구조:

```text
          pipe()
             │
           fork()
          /      \
      Parent     Child
        │          │
     write()     read()
        │          ▲
        └── Pipe ──┘
```

예제에서는:

```text
Parent
→ fd_pipe[0] 닫음
→ fd_pipe[1]에 write()

Child
→ fd_pipe[1] 닫음
→ fd_pipe[0]에서 read()
```

사용하지 않는 파이프 끝은 반드시 닫는 습관이 중요하다.

```text
/* Parent */
close(fd_pipe[0]);

/* Child */
close(fd_pipe[1]);
```

---

<a id="notion-3e31d46c18fc80029dd1cb3ef50afcad"></a>

## 자식이 `read()`를 먼저 실행하면?

가능하다.

```text
read(fd_pipe[0], ...);
```

를 실행했는데 아직 파이프에 데이터가 없다면 기본적인 **blocking pipe**에서는:

```text
Child read()
   ↓
데이터 없음
   ↓
Sleep / Block
   ↓
Parent write()
   ↓
데이터 도착
   ↓
Child 깨어남
   ↓
read() 완료
```

즉 부모가 반드시 먼저 `write()`해야 하는 것은 아니다.

<a id="notion-3e31d46c18fc8024a98aedd8e2b699be"></a>

### 추가로 알아둘 점

데이터가 없고 **쓰기 FD가 아직 열려 있으면**:

```text
read() → 데이터가 들어올 때까지 대기
```

모든 쓰기 끝이 닫혔고 더 이상 데이터도 없다면:

```text
read() → 0
```

즉 EOF가 된다.

# 이름 있는 파이프(FIFO)

FIFO는 파일 시스템에 이름을 가진 파이프이다.

```text
Anonymous Pipe
→ 이름 없음
→ 주로 fork() 관계의 프로세스에서 사용

FIFO
→ 파일 시스템에 이름 존재
→ 서로 관계없는 프로세스도 통신 가능
```

생성:

```text
int mkfifo(const char *pathname, mode_t mode);
```

예:

```text
mkfifo("./my_fifo", 0777);
```

실제로 생성되는 권한은 `umask`의 영향을 받는다.

```text
최종 권한 = mode & ~umask
```

Shell에서도 생성할 수 있다.

```text
mkfifo my_fifo
```

---

<a id="notion-3e31d46c18fc8036ada6c4a74dfe0667"></a>

# FIFO 쓰기 프로세스

```text
fd_fifo = open(PATH_FIFO, O_WRONLY);
```

FIFO를 쓰기 전용으로 연다.

그 후:

```text
write(fd_fifo, wstr, ...);
```

로 데이터를 FIFO에 전달한다.

```text
wfifo
  │
write()
  │
  ▼
my_fifo
```

---

<a id="notion-3e31d46c18fc806f872ae67de85b834a"></a>

# FIFO 읽기 프로세스

```text
fd_fifo = open(PATH_FIFO, O_RDONLY);
```

FIFO를 읽기 전용으로 연다.

```text
read(fd_fifo, rbuf, ...);
```

를 통해 데이터를 받는다.

```text
my_fifo
   │
 read()
   ▼
rfifo
```

전체 구조:

```text
wfifo Process              rfifo Process
     │                          ▲
     │ write()                  │ read()
     ▼                          │
        ──── my_fifo ──────────
```

두 프로그램은 부모-자식 관계가 아니어도 같은 FIFO 경로를 사용하면 통신할 수 있다.

---

<a id="notion-3e31d46c18fc80b796b8dd36fdbad8d8"></a>

## FIFO의 Blocking 동작

기본 blocking mode에서는 FIFO를 한쪽만 열려고 하면 상대편을 기다릴 수 있다.

쓰기 측:

```text
open(PATH_FIFO, O_WRONLY);
```

→ 일반적으로 **reader가 FIFO를 열 때까지 대기**

읽기 측:

```text
open(PATH_FIFO, O_RDONLY);
```

→ 일반적으로 **writer가 FIFO를 열 때까지 대기**

따라서 `wfifo`와 `rfifo` 중 어느 프로그램을 먼저 실행해도 상대방이 연결될 때까지 기다렸다가 통신할 수 있다.

`O_NONBLOCK`을 사용하면 이러한 동작은 달라진다.

# 이름 없는 파이프 vs FIFO

| 구분 | 이름 없는 파이프 | FIFO |
| --- | --- | --- |
| 생성 | `pipe()` | `mkfifo()` |
| 파일 이름 | 없음 | 있음 |
| 접근 | FD | FIFO 파일을 `open()` |
| 주요 용도 | 부모-자식 등 관련 프로세스 | 서로 독립적인 프로세스 |
| 통신 방향 | 기본 단방향 | 기본 단방향 |
| I/O | `read()`, `write()` | `read()`, `write()` |

파이프의 핵심은 동일하다.

```text
Writer
   │
 write()
   ▼
 Pipe / FIFO
   │
 read()
   ▼
Reader
```
