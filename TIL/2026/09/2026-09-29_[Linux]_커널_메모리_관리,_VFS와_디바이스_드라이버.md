## GFP(`gfp_t`) 플래그

GFP(Get Free Pages) 플래그는 Kernel에서 메모리를 할당할 때 **어느 영역에서, 어떤 방식으로 메모리를 확보할지 지정**한다.

<a id="notion-3ea1d46c18fc80d7bb0ce474c2923cf6"></a>

### 영역 지정

```text
__GFP_DMA
→ DMA 영역에서 할당

__GFP_DMA32
→ DMA32 영역에서 할당

__GFP_HIGHMEM
→ High Memory 영역까지 할당 대상으로 사용
```

<a id="notion-3ea1d46c18fc80dd88d8f832be877456"></a>

### 동작 지정

```text
__GFP_IO
→ 메모리 확보 과정에서 I/O 수행 허용

__GFP_FS
→ 메모리 확보 과정에서 파일시스템 관련 작업 허용
```

<a id="notion-3ea1d46c18fc80bfabe9fdaa7701665e"></a>

### 자주 사용하는 유형

<a id="notion-3ea1d46c18fc803291dccecaeb05463a"></a>

#### `GFP_KERNEL`

일반적인 Kernel 메모리 할당에 사용한다.

```text
GFP_KERNEL
→ 일반적인 상황
→ sleep 가능
```

메모리가 부족하면 확보 과정에서 현재 Task가 sleep할 수 있다.

<a id="notion-3ea1d46c18fc801c89e8d264ecdd8cdf"></a>

#### `GFP_ATOMIC`

```text
⭐ GFP_ATOMIC
→ sleep하면 안 되는 상황에서 사용
```

대표적인 사용 상황:

- Interrupt Handler
- Spinlock을 획득한 상태
- Atomic Context

즉 메모리 확보를 위해 **sleep할 수 없는 상황**에서 사용한다.

<a id="notion-3ea1d46c18fc80b7829edfaa423e4336"></a>

#### `GFP_DMA`

DMA 가능한 메모리 영역에서 할당하도록 지정한다.

DMA 영역이 없더라도 타 시스템과의 호환성 때문에 지정해줘야 한다.

## 바이트 단위 메모리 할당

⭐ **시험 ★★★**

대표 함수:

```text
kmalloc()
vmalloc()
```

<a id="notion-3ea1d46c18fc8062b43dcf7b8d884197"></a>

### 공통점

- 요청한 크기를 **Byte 단위**로 할당
- 가상 주소(Kernel Virtual Address) 반환
- 실패 → `NULL` 리턴

---

<a id="notion-3ea1d46c18fc80658cb2d171a8429f3a"></a>

### `kmalloc()`

```text
kmalloc(size, gfp_flags);
```

특징:

- **물리적으로 연속된 메모리** 할당(가상 주소도 연속)
- GFP 플래그를 통해 할당 방식 지정 가능
- 인터럽트 핸들러처럼 sleep을 하면 안되는 상황이면 GFP\_ATOMIC을 사용해야 함
- 일반적인 Kernel 동적 메모리 할당에 사용

```text
일반 상황
→ GFP_KERNEL

sleep 불가능
→ GFP_ATOMIC
```

---

<a id="notion-3ea1d46c18fc8080ab0bc0373205cffd"></a>

### `vmalloc()`

```text
vmalloc(size);
```

특징:

- 가상 주소 공간은 연속, 실제 **물리 페이지는 연속일 필요 없음**
- 큰 메모리 영역을 확보하기에 유리
- `kmalloc()`보다 느림
- sleep할 수 있으므로 Atomic Context에서 사용할 수 없음

```text
kmalloc()
→ 물리적으로 연속
→ 빠름
→ 일반적인 경우 우선 사용

vmalloc()
→ 물리적으로 비연속 가능
→ 상대적으로 느림
→ 큰 메모리 필요 시 사용
```

⚠️ **핵심**

> 특별한 이유가 없다면 `kmalloc()`을 사용하고, 큰 연속 가상 메모리가 필요하지만 물리적 연속성이 필요하지 않다면 `vmalloc()`을 고려한다.

## 선점형 커널 vs 비선점형 커널

- 선점형 커널

  - 커널 코드가 실행 중이어도, 더 우선순위가 높은 태스크가 실행해야 하면 **중간에 CPU를 뺏어갈 수 있는 커널**
  - **커널 안에서도 선점 가능**
  - 응답성이 좋아서 실시간성이 중요한 시스템에 유리
- 비선점형 커널

  - 한 태스크가 커널 코드를 실행하기 시작하면 **중간에 다른 태스크가 강제로 뺏지 못함**
  - **커널 코드 실행이 끝나거나 스스로 양보/대기하기 전까지 계속 실행**

# 페이지의 가상 메모리 매핑

`alloc_page()` 등으로 얻은 `struct page`를 실제로 접근하려면 상황에 따라 가상 메모리(Kernel Virtual Address)가 필요하다.

특히 32bit `HIGHMEM` 환경에서는 High Memory Page가 Kernel 주소 공간에 항상 매핑되어 있지 않기 때문에 **임시 매핑**이 필요할 수 있다.

---

<a id="notion-3ea1d46c18fc80ab8fc4ead5c27d6c8c"></a>

## `kmap()`

```text
void *kmap(struct page *page);
```

Page를 Kernel Virtual Address에 매핑하고 해당 주소를 반환한다.

특징:

- 필요하면 매핑 공간을 확보
- sleep할 수 있음
- **선점 활성 상태에서만 사용 가능**
- 매핑이 전역적으로 보임
- `kunmap()`으로 해제

```text
addr = kmap(page);

/* page 접근 */

kunmap(page);
```

최신 Kernel에서는 `kmap()`보다 `kmap_local_page()` 사용을 권장한다.

---

<a id="notion-3ea1d46c18fc802a843dfd014d612e16"></a>

## `kmap_atomic()`

```text
void *kmap_atomic(struct page *page);
```

sleep할 수 없는 Atomic Context에서 Page를 임시 매핑하기 위해 사용해 온 함수이다.

특징:

- sleep하지 않음
- Interrupt Context 등에서도 사용 가능
- `kunmap_atomic()` 전까지 sleep 가능한 함수 호출 금지
- 선점을 비활성화 시키므로 이후 원자적으로 수행됨
- sleep하지 않으므로 비선점 상태에서도 사용 가능
- 매핑은 CPU 로컬
- `kunmap_atomic()`으로 해제

```text
addr = kmap_atomic(page);

/* sleep 금지 */

kunmap_atomic(addr);
```

⚠️ **현재는 Deprecated**

새 코드에서는:

```text
kmap_local_page()
```

사용을 권장한다.

---

<a id="notion-3ea1d46c18fc80c3bb0cfebc49936259"></a>

## `kmap_local_page()`

```text
void *kmap_local_page(struct page *page);
```

현재 권장되는 Page 임시 매핑 방식이다.

특징:

- 짧은 시간 사용할 Page를 가상 주소에 매핑
- **현재 호출 Context에서만 유효한 Local Mapping**
- 선점 비활성화하지 않음
- 선점 활성이나 비활성 상태 무관하게 사용 가능
- 매핑은 스레드(태스크) 로컬
- Interrupt Context에서도 사용 가능
- `kmap()`보다 빠르고 가벼움
- `kmap()` / `kmap_atomic()` 대신 사용 권장

```text
addr = kmap_local_page(page);

/* page 접근 */

kunmap_local(addr);
```

⚠️ `kmap_local_page()` 자체가 항상 preemption을 비활성화한다고 이해하면 안 된다.

최신 Kernel에서는 필요한 내부 처리를 수행하지만, 호출자가 **preemption 비활성화라는 부수효과에 의존하면 안 된다.**

---

<a id="notion-3ea1d46c18fc803fb7acda226fc83567"></a>

## 매핑 함수 비교

| 함수 | Sleep | 매핑 범위 | 현재 사용 |
| --- | --- | --- | --- |
| `kmap()` | 가능 | Global | Deprecated |
| `kmap_atomic()` | 불가 | Local/Atomic | Deprecated |
| `kmap_local_page()` | Context 제약이 적음 | 현재 호출 Context Local | **권장** |

<a id="notion-3ea1d46c18fc801091c0f0641c28ec35"></a>

### 핵심

```text
kmap()
→ 전역적인 임시 매핑
→ sleep 가능

kmap_atomic()
→ Atomic Context용
→ sleep 불가
→ Deprecated

kmap_local_page()
→ Local Mapping
→ 현재 권장 방식
→ Interrupt Context에서도 사용 가능
```

64bit 시스템은 high memory가 없고 모든 물리 메모리의 가상 메모리가 항상 존재하므로 가상 메모리 할당이 불필요하다

## 프로세스의 User Space 정보

프로세스의 가상 주소 공간 정보는 `/proc`에서 확인할 수 있다.

```text
/proc/PID/maps
```

`/proc/PID/maps` 파일에는 해당 프로세스의 **User Space 메모리 매핑 정보**가 표시된다.

---

<a id="notion-3ea1d46c18fc804e84a4e508c04dc3fd"></a>

## User Address Space

각 프로세스는 자신의 독립적인 주소 공간을 가진다.

```text
Process Address Space
├─ User Space
└─ Kernel Space
```

프로세스마다 주소 공간은 별도로 존재한다.

User Space 내부에는 다음과 같은 여러 메모리 영역이 존재한다.

```text
CODE
RO
RW
Heap
Stack
Shared Library
mmap 영역
...
```

이러한 각각의 메모리 영역을 **VMA(Virtual Memory Area)** 또는 세그먼트 단위로 관리한다.

---

<a id="notion-3ea1d46c18fc8071b053ed74cfdb4fcc"></a>

## User Address Space 표현 — `vm_area_struct`

Kernel은 하나의 가상 메모리 영역을:

```text
struct vm_area_struct
```

로 표현한다.

즉:

```text
vm_area_struct 하나
→ 하나의 Virtual Memory Area
→ 특정 주소 범위와 속성을 표현
```

대표적으로 해당 영역의:

- 시작/끝 주소
- 접근 권한
- 매핑 정보

등을 관리한다.

---

<a id="notion-3ea1d46c18fc80a9a410cd42b8cf95c7"></a>

## User Address Space 관리 — `mm_struct`

프로세스의 전체 메모리 주소 공간은:

```text
struct mm_struct
```

로 관리한다.

`mm_struct`는 여러 개의 `vm_area_struct`를 관리한다.

```text
mm_struct
   ↓
vm_area_struct
vm_area_struct
vm_area_struct
...
```

수업에서 다루는 관리 구조:

<a id="notion-3ea1d46c18fc80c3a001e1655daf6313"></a>

### `mmap`

Linked List 형태로 VMA들을 관리한다.

```text
VMA ↔ VMA ↔ VMA ↔ ...
```

특징:

- 전체 VMA를 순차적으로 탐색하기 편리

<a id="notion-3ea1d46c18fc805b8ae7dd70ee5a6d13"></a>

### `mm_rb`

Red-Black Tree 형태로 VMA들을 관리한다.

특징:

- 특정 주소에 해당하는 VMA를 빠르게 검색하기 유리

```text
mmap
→ 전체 순회에 유리

mm_rb
→ 특정 VMA 검색에 유리
```

# 파일시스템(File System)

<a id="notion-3ea1d46c18fc8042bf93cd1a2c5e576b"></a>

## 파일시스템

프로그램과 데이터는 저장장치에 저장되어야 한다.

대표적인 저장 매체:

```text
HDD
USB Memory
ROM
RAM
SD Card
MMC Card
Remote Server
...
```

파일시스템은 저장장치의 데이터를 관리하고, 파일에 대한 \*\*메타데이터(Metadata)\*\*를 함께 제공한다.

메타데이터의 예:

```text
파일 이름
파일 크기
저장 위치
파일 속성
수정 시간
권한
...
```

---

<a id="notion-3ea1d46c18fc806bbdb1fa41069ad2d1"></a>

## 파일 데이터 저장

파일 데이터는 가능하면 연속된 저장 공간에 존재하는 것이 효율적이다.

하지만 실제 저장장치에서는 파일의 데이터가 여러 조각으로 나뉘어 저장될 수 있다.

```text
File
 ↓
Data Block
Data Block
Data Block
...
```

파일시스템은 이러한 실제 저장 위치와 파일 정보를 관리한다.

---

<a id="notion-3ea1d46c18fc80d79ff6d0855923a2b2"></a>

## 파일시스템의 종류

운영체제, 저장 매체, 목적에 따라 다양한 파일시스템이 존재한다.

<a id="notion-3ea1d46c18fc8088b92bda931bc16abf"></a>

### Windows

```text
FAT16
FAT32
NTFS
```

<a id="notion-3ea1d46c18fc808a9b70da95c77ff50f"></a>

### Linux

```text
ext2
ext3
ext4
```

또한 특정 제품이나 저장 매체에 최적화된 별도의 파일시스템을 사용할 수도 있다.

예:

```text
NAND Flash
CD-ROM
특정 Embedded Storage
```

현재 Kernel에서 지원하는 파일시스템은:

```text
cat /proc/filesystems
```

로 확인할 수 있다.

---

<a id="notion-3ea1d46c18fc80aa937aedb4415f2e07"></a>

# VFS(Virtual File System)

VFS는 서로 다른 파일시스템들을 **공통된 인터페이스로 사용할 수 있도록 하는 Kernel 계층**이다.

```text
Application
    ↓
 open/read/write
    ↓
   VFS
    ↓
┌───────────────┐
ext4   FAT   기타 FS
└───────────────┘
    ↓
Storage Device
```

응용 프로그램은 실제 파일시스템이나 저장 매체의 종류를 직접 신경 쓰지 않고 동일한 파일 API를 사용할 수 있다.

즉:

> **VFS는 여러 종류의 파일시스템을 응용 프로그램 입장에서 하나의 파일시스템처럼 보이게 한다.**

---

<a id="notion-3ea1d46c18fc80dfac87d9cc8fb6cc37"></a>

# ext2 / ext3 / ext4 파일시스템 구조

저장장치는 하나의 파티션으로 사용할 수도 있고 여러 개의 파티션으로 나눌 수도 있다.

파일시스템의 저장 공간은 계층적으로 관리된다.

```text
Sector
  ↓
Block
  ↓
Block Group
```

<a id="notion-3ea1d46c18fc8025bebacb97e7b8e707"></a>

### Sector

저장장치가 데이터를 처리하는 물리적 단위.

<a id="notion-3ea1d46c18fc80078eeede0f1962d14c"></a>

### Block

파일시스템에서 사용하는 **논리적인 데이터 관리 단위**.

<a id="notion-3ea1d46c18fc80e8a64ef97fb465e718"></a>

### Block Group

여러 Block을 묶어서 관리하는 단위.

---

<a id="notion-3ea1d46c18fc803d9824f5451c080737"></a>

## Super Block

파일시스템의 전체적인 중요 정보를 저장한다.

대표 정보:

```text
전체 Block 개수
Block 크기
파일시스템 크기
상태 정보
...
```

즉 **파일시스템 전체에 대한 핵심 메타데이터**를 관리한다.

---

<a id="notion-3ea1d46c18fc80189ca6cd65007655c4"></a>

## Inode Table

파일의 메타데이터를 저장하는 Inode들의 집합이다.

대표적으로:

```text
파일 크기
파일 권한
파일 수정 시간
데이터 Block 위치 정보
...
```

를 관리한다.

⚠️ 파일 이름 자체는 일반적으로 Inode에 저장되는 것이 아니라 Directory Entry가 Inode를 연결하는 형태로 관리된다.

---

<a id="notion-3ea1d46c18fc80519b0ac14a67a07978"></a>

## Data Blocks

파일의 \*\*실제 내용(Data)\*\*이 저장되는 영역이다.

```text
File
├─ Metadata → Inode
└─ 실제 내용 → Data Blocks
```

<a id="notion-3ea1d46c18fc8096a12ac18f3d488391"></a>

### 구조 핵심

```text
ext2/3/4

Super Block
→ 파일시스템 전체 정보

Inode Table
→ 파일별 메타데이터

Data Blocks
→ 파일의 실제 데이터
```

<a id="notion-3ea1d46c18fc808e94addb7dc7e7a623"></a>

## VFS 주요 객체

⭐ **시험 ★★★★ — VFS 주요 객체 4개 중요**

VFS(Virtual File System)는 서로 다른 파일시스템을 공통된 형태로 다루기 위해 주요 객체들을 사용한다.

```text
super_block
inode
dentry
file
```

---

<a id="notion-3ea1d46c18fc8000b9cfcf79bf9d2d82"></a>

### `super_block` 객체

파일시스템의 **Super Block 정보**를 처리한다.

- 파티션을 마운트할 때마다 `super_block` 객체 생성
- 파일시스템 전체에 대한 정보를 관리
- 파일시스템 종류에 따라 내부 구성이 달라질 수 있음
- 본체와 Operations로 구성

주요 멤버:

```text
s_blocksize
→ 파일시스템 Block 크기

s_type
→ 파일시스템 종류

s_op
→ Super Block 관련 Operations
```

---

<a id="notion-3ea1d46c18fc80698e02c490a0d1c31e"></a>

### `inode` 객체

파일의 **메타데이터**를 처리한다.

대표적으로:

```text
파일 크기
수정 시간
파일 번호
권한
...
```

- 사용되는 파일마다 `inode` 객체가 생성됨
- 파일시스템마다 메타데이터 저장 방식은 다르지만 VFS에서는 `inode` 형식에 맞게 표현

주요 멤버:

```text
i_sb
→ 해당 inode가 속한 super_block

i_ino
→ inode 번호

i_size
→ 파일 크기

i_mtime
→ 파일 수정 시간

i_op
→ inode 관련 Operations
```

---

<a id="notion-3ea1d46c18fc80b79fe9f8cc6a89b8c6"></a>

### `dentry` 객체

파일 경로의 **각 구성 요소**를 표현한다.

예:

```text
/bin/ls
```

이면:

```text
/
bin
ls
```

각각이 `dentry` 객체로 표현된다.

- 파일 경로 관리에 사용
- 파일 접근 과정에서 `file` 객체와 `inode` 객체를 연결
- VFS가 디렉터리 탐색 과정에서 필요에 따라 생성

주요 멤버:

```text
d_parent
→ 부모 dentry

d_inode
→ 연결된 inode

d_iname[]
→ 파일/디렉터리 이름

d_op
→ dentry 관련 Operations
```

---

<a id="notion-3ea1d46c18fc804e84fbccad0a72798f"></a>

### `file` 객체

**열린 파일 하나**를 표현하며 실제 파일의 읽기/쓰기 작업에 관여한다.

- 같은 파일이라도 여러 번 `open()`하면 각각 별도의 `file` 객체가 생성될 수 있음
- 열린 파일마다 현재 접근 위치 등을 따로 관리

주요 멤버:

```text
f_path
→ 파일 경로 정보

f_flags
→ open 시 사용한 Flag // O_RDONLY...

f_pos
→ 현재 파일 접근 위치

f_op
→ 파일 관련 Operations
```

---

<a id="notion-3ea1d46c18fc80e7a37acb0a7b6743f1"></a>

## ⭐ VFS 객체 간 연결 관계

```text
저장 매체
   ↑
super_block
   ↑
inode
   ↑
dentry
   ↑
file
   ↑
files_struct // 파일 식별자 테이블
   ↑
task_struct
```

```text
task_struct
→ Task 정보

files_struct
→ 해당 Task의 열린 파일 / FD 관련 정보

file
→ 열린 파일 하나

dentry
→ 경로의 구성 요소

inode
→ 파일의 메타데이터

super_block
→ 파일시스템 전체 정보

저장 매체
→ 실제 데이터가 저장되는 장치
```

⭐ **핵심 암기**

> `task_struct → files_struct → file → dentry → inode → super_block → 저장 매체`

# 디바이스 제어

<a id="notion-3ea1d46c18fc80b5803fc42d3837cf22"></a>

## 디바이스 드라이버

<a id="notion-3ea1d46c18fc807a9a49f2c6e8c8c4b8"></a>

### 디바이스 드라이버의 종류

리눅스의 디바이스 드라이버는 크게 3종류로 구분한다.

<a id="notion-3ea1d46c18fc8050a569fc62b8ff24d1"></a>

#### 문자 디바이스 드라이버

GPIO, Serial 등의 **문자 디바이스**를 제어한다.

- 대부분의 디바이스가 문자 디바이스 형태로 사용됨

<a id="notion-3ea1d46c18fc80c6892aee3273c8fa4a"></a>

#### 블록 디바이스 드라이버

HDD, SD Card 등의 **블록 디바이스**를 제어한다.

- 블록 단위로 데이터를 처리
- 파일시스템과 함께 사용

<a id="notion-3ea1d46c18fc800abd50e34bb20f2e30"></a>

#### 네트워크 인터페이스 드라이버

Ethernet, Wireless LAN 등의 **네트워크 디바이스**를 제어한다.

---

<a id="notion-3ea1d46c18fc80989b7ec85305d50c90"></a>

## 디바이스 파일

디바이스 파일을 `read()` / `write()`하면 해당 디바이스 파일과 연결된 **디바이스 드라이버가 동작**한다.

디바이스 파일은 주로:

```text
/dev
```

디렉터리에 존재한다.

<a id="notion-3ea1d46c18fc80f4b4caec0221c51eb2"></a>

### 일반 파일과 디바이스 파일의 차이

`ls -l`로 확인하면:

```text
일반 파일     → -
문자 디바이스 → c
블록 디바이스 → b
```

일반 파일은 파일 크기가 표시되지만, 디바이스 파일은 해당 위치에:

```text
Major 번호, Minor 번호
```

가 표시된다.

---

<a id="notion-3ea1d46c18fc8001ac4bca98c81ab9a0"></a>

## `mknod` 명령

📝 **시험 가능성 ★**

디바이스 파일을 직접 생성할 때 사용한다.

예:

```text
sudo mknod /dev/mycdev c 125 0
```

의미:

```text
/dev/mycdev → 생성할 디바이스 파일

c
→ 문자 디바이스 파일

125
→ Major 번호

0
→ Minor 번호
```

디바이스 파일만 생성하고 연결된 디바이스 드라이버가 없다면 정상적으로 사용할 수 없다.

---

<a id="notion-3ea1d46c18fc80369cffc5db066e181f"></a>

## Major 번호와 Minor 번호

<a id="notion-3ea1d46c18fc809bb054dce117f0ee15"></a>

### Major 번호

**디바이스 드라이버를 식별하는 번호**이다.

```text
Major
→ 어떤 디바이스 드라이버를 사용할 것인가
```

- 디바이스 드라이버는 자신의 Major 번호를 가짐
- 같은 종류 내에서는 Major 번호로 드라이버를 구분
- 문자 디바이스와 블록 디바이스는 동일한 숫자의 Major 번호를 각각 사용할 수 있음

---

<a id="notion-3ea1d46c18fc8005ac96e00b08e6f8e3"></a>

### Minor 번호

**하나의 디바이스 드라이버가 관리하는 개별 장치를 구분하는 번호**이다.

```text
Minor
→ 그 드라이버가 관리하는 어떤 장치인가
```

하나의 Major 번호에 여러 Minor 번호를 사용할 수 있다.

예:

```text
/dev/ram0
/dev/ram1
```

같은 드라이버를 사용하더라도 Minor 번호에 따라 서로 다른 장치를 구분하거나 다른 동작을 수행할 수 있다.

---

<a id="notion-3ea1d46c18fc80809acad64b7288d642"></a>

## Major / Minor 관계

```text
Major
→ Device Driver 구분

Minor
→ 해당 Driver가 관리하는 Device 구분
```

예:

```text
Major 125
 ├─ Minor 0 → Device 0
 ├─ Minor 1 → Device 1
 └─ Minor 2 → Device 2
```

Major / Minor 번호는 기존에 정해진 값을 사용하기도 하며, 필요한 경우 Major 번호를 동적으로 할당받거나 사용 가능한 번호를 사용할 수 있다.

<a id="notion-3ea1d46c18fc8054b1bcdc3b928b0fc2"></a>

# 리눅스 모듈

<a id="notion-3ea1d46c18fc8010a75cfb10dff9a431"></a>

## 모듈

Kernel 구성 요소와 Device Driver를 **Module** 형태로 만들 수 있다.

- Module은 Kernel 영역에 동적으로 Load / Unload 가능
- Load 후에는 Kernel 코드와 동일하게 동작
- 필요한 기능만 동적으로 올릴 수 있어 Kernel Image 크기를 줄일 수 있음
- Module Utility를 이용하여 관리

주요 명령:

```text
sudo insmod hello.ko   # Module Load
sudo rmmod hello       # Module Unload
lsmod                  # 현재 Load된 Module 확인
```

기본 실행 흐름:

```text
make
→ sudo insmod hello.ko
→ sudo dmesg | tail
→ lsmod
→ sudo rmmod hello
```

---

<a id="notion-3ea1d46c18fc8027a5eef70a4899fa20"></a>

## 기본 Module 구현

```text
#include <linux/init.h>
#include <linux/module.h>

static int __init hello_init(void)
{
    printk("Hello!\n");
    return 0;
}

static void __exit hello_exit(void)
{
    printk("Goodbye!\n");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
```

```text
hello_init()
→ Module Load 시 실행

hello_exit()
→ Module Unload 시 실행
```

---

<a id="notion-3ea1d46c18fc80f29fd2c7e6ebc937af"></a>

## Module 시작 / 종료 매크로 — Module로 사용 시

```text
module_init(hello_init);
module_exit(hello_exit);
```

Module로 컴파일하면:

```text
module_init(hello_init)
→ init_module() 대신 hello_init() 사용

module_exit(hello_exit)
→ cleanup_module() 대신 hello_exit() 사용
```

즉:

```text
insmod
→ hello_init()

rmmod
→ hello_exit()
```

---

<a id="notion-3ea1d46c18fc80ddab14fa9fe68327ee"></a>

## Module 시작 / 종료 매크로 — Kernel에 포함 시

<a id="notion-3ea1d46c18fc8070925df8550beea4a6"></a>

### `module_init(hello_init)`

1. `__initcall_...hello_init6` 형태의 함수 포인터 생성
2. `hello_init` 함수 주소 저장
3. `.initcall6.init` Section에 배치
4. Kernel 초기화 과정에서 `hello_init()` 자동 호출

<a id="notion-3ea1d46c18fc80d1a044e57d02d22b59"></a>

### `module_exit(hello_exit)`

1. `__exitcall_hello_exit` 형태의 함수 포인터 생성
2. `hello_exit` 함수 주소 저장
3. Kernel에 포함하여 사용할 경우 종료 코드는 의미가 없어 제외됨

---

<a id="notion-3ea1d46c18fc80a0ac08e52ba753a5db"></a>

## 📝 Module 시작 / 종료 매크로 정리

📝 **시험 가능성 ★**

```text
module_init(f1);
module_exit(f2);
```

<a id="notion-3ea1d46c18fc804e9027fd52e1c5b48d"></a>

### Module로 컴파일

```text
insmod
→ init_module() 대신 f1() 호출

rmmod
→ cleanup_module() 대신 f2() 호출
```

<a id="notion-3ea1d46c18fc807db4d0fc24c744329e"></a>

### Kernel에 포함하여 컴파일

```text
f1()
→ Kernel 초기화 과정에서 자동 호출

f2()
→ 의미 없음
```

<a id="notion-3ea1d46c18fc80f78336db056265c488"></a>

### 사용하는 이유

> **소스코드를 수정하지 않고 동일한 코드를 Module로 컴파일하거나 Kernel에 포함하여 컴파일할 수 있다.**

---

<a id="notion-3ea1d46c18fc802e9714c53a9e301a21"></a>

## 기타 Module 매크로

대부분의 Module 매크로는 내부적으로 정보를 담기 위한 변수를 생성한다.

예:

```text
MODULE_LICENSE("GPL");
```

내부적으로는 `"license=GPL"`과 같은 정보를 가진 변수가 생성된다.

# Module Parameter

Module을 Load할 때 외부에서 값을 전달할 수 있다.

<a id="notion-3ea1d46c18fc80508c88c352ff91978d"></a>

## 단일 Parameter

```text
static int p_int = 10;

module_param(p_int, int, S_IRUGO | S_IWUSR);
```

```text
p_int
→ Parameter 변수

int
→ Parameter 자료형

S_IRUGO | S_IWUSR
→ Parameter 접근 권한
```

Load 시 값을 전달:

```text
sudo insmod para.ko p_int=11
```

---

<a id="notion-3ea1d46c18fc80429f3eef4de24cf686"></a>

## 배열 Parameter

```text
static int pa_int[] = {1, 2, 3, 4};
static int count;

module_param_array(pa_int, int, &count, 0);
```

```text
pa_int
→ Parameter 배열

int
→ 배열 요소 자료형

count
→ 실제로 전달된 배열 요소 개수 저장
```

예:

```text
sudo insmod para.ko pa_int=10,20
```

이면 전달된 값에 따라 `pa_int`가 설정되고 `count`에 전달된 원소 개수가 저장된다.

---

<a id="notion-3ea1d46c18fc8087a575f03d4dbb59f0"></a>

## Module Parameter 예제

```text
static int p_int = 10;

static int pa_int[] = {1, 2, 3, 4};
static int count;

module_param(p_int, int, S_IRUGO | S_IWUSR);
module_param_array(pa_int, int, &count, 0);
```

Module Load:

```text
sudo insmod para.ko p_int=11 pa_int=10,20
```

Module Parameter는 다음 경로에서 확인할 수 있다.

```text
cd /sys/module/para/parameters
ls -l
```

값 확인:

```text
cat p_int
```

값 변경:

```text
sudo sh -c 'echo 12 > p_int'
```

다시 확인:

```text
cat p_int
```

즉 Module Parameter는:

```text
insmod 시 값 전달
        ↓
Module 내부 변수에 반영
        ↓
/sys/module/<module>/parameters
        ↓
Parameter 확인 및 권한에 따라 변경 가능
```

<a id="notion-3ea1d46c18fc808d83d9e26e6ba3c293"></a>

# 오늘 배운 내용 요약정리

<a id="notion-3ea1d46c18fc80409448c9881f428f66"></a>

## Kernel Memory

- `GFP_KERNEL` → sleep 가능
- `GFP_ATOMIC` → sleep 불가
- `kmalloc()` → 물리 연속
- `vmalloc()` → 물리 비연속 가능
- `kmap()` → sleep 가능
- `kmap_atomic()` → atomic context
- `kmap_local_page()` → 현재 권장 방식

<a id="notion-3ea1d46c18fc80b9ae97e28fa6949f72"></a>

## Process Memory

- `/proc/PID/maps`
- `vm_area_struct` → VMA 1개
- `mm_struct` → 프로세스 전체 주소 공간

<a id="notion-3ea1d46c18fc809fb550c742e3239830"></a>

## File System / VFS

- VFS → 여러 파일시스템 공통 인터페이스
- `super_block` → 파일시스템 정보
- `inode` → 파일 메타데이터
- `dentry` → 경로 요소
- `file` → 열린 파일

⭐ `task_struct → files_struct → file → dentry → inode → super_block`

<a id="notion-3ea1d46c18fc802dacd3ea7fca73737f"></a>

## Device Driver

- 문자 / 블록 / 네트워크 드라이버
- `/dev` → 디바이스 파일
- Major → 드라이버 구분
- Minor → 장치 구분
- `mknod` → 디바이스 파일 생성

<a id="notion-3ea1d46c18fc808a851fc8afb3a0c09e"></a>

## Linux Module

- `insmod` → 로드
- `rmmod` → 언로드
- `lsmod` → 모듈 확인
- `module_init()` → 시작 함수
- `module_exit()` → 종료 함수
- `module_param()` → 모듈 파라미터
- `/sys/module/<module>/parameters` → 파라미터 확인/변경
