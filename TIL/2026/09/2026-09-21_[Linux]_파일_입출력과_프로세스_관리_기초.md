# Linux 저수준 파일 입출력

<a id="notion-3e21d46c18fc807d82d8db7c9fa2ff95"></a>

### 개념

<a id="notion-3e21d46c18fc80af9547cf0e0546c7a1"></a>

## 저수준 파일 입출력 (Low-level File I/O)

Linux의 저수준 파일 입출력은 주로 다음 함수를 사용한다.

```text
open()
close()
read()
write()
```

이 함수들은 userspace 프로그램에서 사용하며, 실제 파일 처리는 **system call을 통해 kernel이 수행**한다.

```text
User Space
   │
   │ open(), read(), write(), close()
   ▼
System Call Interface
   │
   ▼
Kernel
   │
   ├─ VFS / File System
   ├─ Device Driver
   │
   ▼
Hardware / Storage Device
```

> 정확히는 `open()`, `read()` 등은 보통 **libc wrapper function**이고, 내부에서 해당 system call을 호출한다.

파일을 열면 프로세스는 파일 자체를 직접 다루는 대신 **File Descriptor(FD)** 라는 정수 값을 사용한다.

---

<a id="notion-3e21d46c18fc80358bb9cf5fceaf3b69"></a>

## Kernel의 역할

Linux에서 kernel은 다음과 같은 핵심 자원을 관리한다.

```text
Process
Memory
File
Device
CPU Scheduling
Interrupt
```

따라서 파일 입출력 역시 프로세스가 하드웨어를 직접 제어하는 것이 아니라 kernel을 거친다.

```text
User Process
    ↓
System Call
    ↓
Kernel
    ↓
File System / Device Driver
    ↓
Hardware
```

# File Descriptor (FD)

<a id="notion-3e21d46c18fc800da8f9e4f533d43e73"></a>

## 개념

**File Descriptor**는 프로세스가 열린 파일을 식별하기 위해 사용하는 `int`형 번호이다.

```text
int fd;

fd = open("a.txt", O_RDWR);
```

예:

```text
fd = 3
```

프로세스 내부에는 FD를 관리하는 테이블이 존재한다.

개념적으로:

```text
Process
 │
 └─ File Descriptor Table
      │
      ├─ 0 → stdin
      ├─ 1 → stdout
      ├─ 2 → stderr
      ├─ 3 → a.txt
      └─ 4 → device
```

---

<a id="notion-3e21d46c18fc80dab16af974ef11c712"></a>

# 표준 File Descriptor

Linux process가 일반적으로 시작할 때 다음 FD가 열려 있다.

| FD | 이름 | 의미 |
| --- | --- | --- |
| `0` | `stdin` | 표준 입력 |
| `1` | `stdout` | 표준 출력 |
| `2` | `stderr` | 표준 에러 |

하지만 FD가 반드시 특정 장치를 의미하는 것은 아니다.

예:

```text
./main > output.txt
```

이 경우:

```text
fd 1 (stdout)
   ↓
output.txt
```

로 redirect된다.

따라서:

> `0`, `1`, `2`는 표준 입출력의 **번호**이고, 실제 연결 대상은 상황에 따라 달라질 수 있다.

# Linux의 "Everything is a File" 개념

Linux에서는 일반 파일뿐 아니라 다양한 kernel object를 FD를 이용해 접근한다.

예:

```text
Regular File
Device File
Pipe
Socket
Terminal
```

따라서:

```c
read(fd, ...);
write(fd, ...);
```

같은 공통 interface를 사용할 수 있다.

Device Driver를 공부할 때 매우 중요한 개념이다.

```text
User Application
      │
   read(fd)
      │
      ▼
System Call
      │
      ▼
Kernel
      │
      ▼
Device Driver
      │
      ▼
Hardware
```


# `open()` flags

파일의 open 방식 지정.

Access Mode는 하나를 지정한다.

```text
O_RDONLY
O_WRONLY
O_RDWR
```

추가 flag는 bitwise OR로 조합할 수 있다.

```text
O_WRONLY | O_CREAT | O_EXCL
```

<a id="notion-3e21d46c18fc80c2b6cfd45c0e733c5b"></a>

## `O_CREAT`

파일이 존재하지 않으면 새 파일 생성.

```text
open("a.txt",
     O_WRONLY | O_CREAT,
     S_IRUSR | S_IWUSR);
```

<a id="notion-3e21d46c18fc80db833bd29d126a08fd"></a>

### 오타 주의

```text
O_CREATE  ❌
O_CREAT   ✅
```

---

<a id="notion-3e21d46c18fc80439a97fc0170df9a59"></a>

## `O_EXCL`

보통 `O_CREAT`와 함께 사용한다.

```text
O_CREAT | O_EXCL
```

의미:

```text
파일 없음
→ 생성

파일 존재
→ open() 실패
```

기존 파일을 실수로 덮어쓰는 것을 막을 수 있다.

# `O_NONBLOCK`

```text
O_NONBLOCK
```

I/O operation에서 **non-blocking 동작을 요청**한다.

예를 들어 device나 pipe에서 당장 읽을 데이터가 없다면 blocking I/O는 기다릴 수 있다.

```text
Blocking

read()
  ↓
데이터 없음
  ↓
Process Sleep
  ↓
데이터 도착
  ↓
Wake-up
```

Non-blocking에서는 보통:

```text
read()
  ↓
데이터 없음
  ↓
즉시 error 반환
```

대표적으로:

```text
errno = EAGAIN
```

또는

```text
EWOULDBLOCK
```

<a id="notion-3e21d46c18fc80b498d4d9e64a82133e"></a>

### 수정할 부분

필기의

```text
blocking = sleep 가능
nonblocking = sleep 불가능
```

은 너무 단순화되어 있다.

더 정확하게는:

> `O_NONBLOCK`은 해당 I/O operation이 조건이 만족될 때까지 기다리며 block되는 것을 피하도록 요청하는 flag이다.

프로세스 자체가 모든 상황에서 절대 sleep하지 않는다는 뜻은 아니다.

# `mode`

`O_CREAT`로 파일이 새로 생성될 때 사용할 permission을 지정한다.

```text
open("test.txt",
     O_WRONLY | O_CREAT,
     S_IRUSR | S_IWUSR);
```

`mode`는 최종적으로 `umask`의 영향도 받는다.

개념적으로:

```text
실제 permission = mode & ~umask
```

---

<a id="notion-3e21d46c18fc8045a37bd9896dd90c63"></a>

## 📝 시험 포인트 — 파일 생성 권한과 `umask`

시험 형태는 대략 다음 흐름이다.

```text
open()의 mode 권한 제시
+
umask 값 제시
↓
최종 파일 접근 권한을 8진수로 계산
```

핵심 공식:

```text
최종 권한 = mode & ~umask
```

---

<a id="notion-3e21d46c18fc809fa7b1fe4c0f1b9969"></a>

### 1\. 기본 권한 값 읽기

대표적인 permission macro:

```text
S_IRUSR = 0400   // owner read
S_IWUSR = 0200   // owner write
S_IXUSR = 0100   // owner execute

S_IRGRP = 0040   // group read
S_IWGRP = 0020   // group write
S_IXGRP = 0010   // group execute

S_IROTH = 0004   // other read
S_IWOTH = 0002   // other write
S_IXOTH = 0001   // other execute
```

묶음 macro:

```text
S_IRWXU = 0700
S_IRWXG = 0070
S_IRWXO = 0007
```

---

<a id="notion-3e21d46c18fc80d5a79adae7eb46141e"></a>

### 2\. `rwx`와 8진수 대응

```text
r = 4
w = 2
x = 1
```

따라서:

```text
rwx = 7
rw- = 6
r-x = 5
r-- = 4
-w- = 2
--x = 1
--- = 0
```

예:

```text
rw-r--r--
```

계산:

```text
owner : rw- = 4 + 2 = 6
group : r-- = 4
other : r-- = 4

→ 0644
```

---

<a id="notion-3e21d46c18fc802cacddc820730cd83d"></a>

## 3\. `umask`의 의미

`umask`는 **새 파일 생성 시 제거할 권한을 지정하는 값**이다.

예:

```text
mode  = 0666
umask = 0022
```

계산:

```text
0666
& ~0022
------
0644
```

최종 권한:

```text
0644
```

즉:

```text
rw-r--r--
```

---

<a id="notion-3e21d46c18fc80e0a507eaa31866a36c"></a>

## 📝 시험 계산 방법

시험에서는 아래 순서대로 하면 된다.

<a id="notion-3e21d46c18fc802f9986daed38877044"></a>

### 예제 1

```text
open("a.txt",
     O_WRONLY | O_CREAT,
     S_IRUSR | S_IWUSR |
     S_IRGRP |
     S_IROTH);
```

주어진 `umask`:

```text
0022
```

먼저 `mode` 계산:

```text
S_IRUSR = 0400
S_IWUSR = 0200
S_IRGRP = 0040
S_IROTH = 0004

mode = 0644
```

이제:

```text
0644 & ~0022
```

`umask`에서 제거하려는 권한은 이미 `mode`에 없기 때문에:

```text
최종 권한 = 0644
```

---

<a id="notion-3e21d46c18fc80fead1efd7fc4538003"></a>

## 예제 2

```text
open("a.txt",
     O_WRONLY | O_CREAT,
     S_IRWXU |
     S_IRWXG |
     S_IRWXO);
```

즉:

```text
mode = 0777
```

`umask`:

```text
0022
```

계산:

```text
0777
& ~0022
------
0755
```

최종 답:

```text
0755
```

권한:

```text
rwxr-xr-x
```

---

<a id="notion-3e21d46c18fc80889f1bffa589e0febb"></a>

## 예제 3

```text
mode  = 0666
umask = 0002
```

계산:

```text
0666
& ~0002
------
0664
```

최종 권한:

```text
0664
```

```text
rw-rw-r--
```

<a id="notion-3e21d46c18fc803f9513e3a51538aaaf"></a>

# ⚠️ 시험에서 자주 헷갈리는 부분

`umask`는 **권한 값을 빼는 것**이 아니다.

다음처럼 계산하면 안 된다.

```text
0666 - 0022   ❌
```

반드시 bit mask 방식이다.

```text
0666 & ~0022   ✅
```

다만 단순한 문제에서는 결과가 우연히 뺄셈처럼 보일 수 있어서 헷갈리기 쉽다.

---

<a id="notion-3e21d46c18fc803191b4ccc1aa2cf6da"></a>

# 📝 빠른 계산법

시험에서는 각 자리별로 `umask`가 막는 bit를 제거한다고 생각하면 빠르다.

예:

```text
mode  = 0777
umask = 0022
```

자리별로 보면:

```text
owner : 7 & ~0 = 7
group : 7 & ~2 = 5
other : 7 & ~2 = 5
```

따라서:

```text
0755
```

또는:

```text
rwx rwx rwx
    ↓   ↓
    w 제거

rwx r-x r-x
```

---

<a id="notion-3e21d46c18fc80a5a1fdd5c8427b2c2e"></a>

# 📝 시험 직전 암기

```text
최종 권한 = mode & ~umask
```

```text
r = 4
w = 2
x = 1
```

```text
S_IRUSR = 0400
S_IWUSR = 0200
S_IXUSR = 0100

S_IRGRP = 0040
S_IWGRP = 0020
S_IXGRP = 0010

S_IROTH = 0004
S_IWOTH = 0002
S_IXOTH = 0001
```

```text
S_IRWXU = 0700
S_IRWXG = 0070
S_IRWXO = 0007
```

대표 패턴:

```text
0666 + umask 0022 → 0644
0777 + umask 0022 → 0755
0666 + umask 0002 → 0664
```

<strong>시험에서는</strong> **`mode → 8진수 변환 → umask 적용 → 최종 8진수`** <strong>순서로 풀면 된다.</strong>

# `read()`

```text
ssize_t read(
    int fd,
    void *buf,
    size_t count
);
```

의미:

```text
fd에서 최대 count byte를 읽어서
buf에 저장
```

반환값:

```text
> 0 : 실제 읽은 byte 수
  0 : EOF
 -1 : error
```

예:

```text
char c;

ret = read(fd, &c, 1);
```

파일에서 최대 1 byte 읽는다.

---

<a id="notion-3e21d46c18fc80cbb989cff81d05467e"></a>

# `write()`

```text
ssize_t write(
    int fd,
    const void *buf,
    size_t count
);
```

의미:

```text
buf에 있는 데이터를
fd에 최대 count byte 기록
```

반환값:

```text
>= 0 : 실제 기록한 byte 수
-1    : error
```

<a id="notion-3e21d46c18fc80489ad8ea19563fc59a"></a>

### 중요한 점

```text
write(fd, buf, 100);
```

했다고 반드시 `100 byte`가 한 번에 기록된다고 보장되는 것은 아니다.

예:

```text
요청: 100 byte
반환: 60

→ 나머지 40 byte를 다시 write해야 함
```

이를 **partial write**라고 한다.

## 파일 쓰기

```text
write(fd, &c, 1);
```

한 번에 `1 byte`씩 기록한다.

동작:

```text
Userspace
   ↓
write()
   ↓
System Call
   ↓
Kernel
   ↓
File System
```

이 방식은 학습용으로는 좋지만 성능은 좋지 않다.

```text
1 byte write
→ system call

1 byte write
→ system call

1 byte write
→ system call
...
```

System call overhead가 계속 발생하기 때문이다.

실무에서는 보통 buffer 단위로 처리한다.

# 파일 복사 Loop

```text
for (;;)
{
    ret = read(src_fd, &c, 1);

    if (ret == -1)
        ...

    if (ret == 0)
        break;

    write(dst_fd, &c, 1);

    copied++;
}
```

핵심은 `read()` 반환값이다.

```text
read() > 0
→ 데이터 읽음

read() == 0
→ EOF
→ 복사 종료

read() == -1
→ Error
```

이 패턴은 Linux I/O 코드에서 매우 중요하다.

# ⚠️ 코드에서 보완하면 좋은 점

수업 예제이므로 개념 학습에는 문제없지만 실제 코드를 작성한다면 몇 가지 개선점이 있다.

<a id="notion-3e21d46c18fc80808888dccffb67fbdc"></a>

### 1\. Error 발생 시 열린 FD를 닫아야 함

예:

```text
src_fd = open(...);

dst_fd = open(...);

if (dst_fd == -1)
{
    close(src_fd);
    return EXIT_FAILURE;
}
```

현재 코드는 `dst_fd` open 실패 시 `src_fd`를 닫지 않고 종료한다.

프로세스 종료 시 kernel이 결국 정리하긴 하지만 **resource cleanup 습관**이 중요하다.

---

<a id="notion-3e21d46c18fc8083acacffd0ade84c44"></a>

### 2\. `write()` 반환값 확인

현재:

```text
ret = write(dst_fd, &c, 1);

if (ret == -1)
```

1 byte write라서 간단한 예제에서는 크게 문제될 가능성이 낮지만 일반적인 코드에서는:

```text
requested bytes == returned bytes
```

인지 확인해야 한다.

---

<a id="notion-3e21d46c18fc80d2b37be6128aff00bb"></a>

### 3\. 1 byte 단위 I/O는 비효율적

현재:

```text
char c;

read(fd, &c, 1);
write(fd, &c, 1);
```

실제로는 보통:

```text
char buf[4096];
```

처럼 buffer를 사용한다.

```text
read 4096 byte
       ↓
write 4096 byte
```

System call 횟수가 크게 줄어든다.

# 전체 흐름 정리

오늘 오전 내용에서 가장 중요한 흐름은 이것이다.

```text
Application
     │
     │ open()
     ▼
System Call
     │
     ▼
Kernel
     │
     ├─ FD 관리
     ├─ VFS
     ├─ File System
     └─ Device Driver
              │
              ▼
           Hardware
```

메모리 관점에서는:

```text
Process
   │
Virtual Address
   │
   ▼
  MMU
   │
Page Table
   │
   ▼
Physical Address
   │
   ├─ RAM
   └─ MMIO
```

그리고 파일 I/O 관점에서는:

```text
open()
  ↓
FD 획득
  ↓
read() / write()
  ↓
close()
```

# 📝 시험 직전 체크

오전 내용에서는 이 정도를 우선 기억하면 된다.

```text
1. open() 성공 → FD 반환
2. open() 실패 → -1 + errno
3. FD는 프로세스별로 관리
4. 0 = stdin
   1 = stdout
   2 = stderr

5. O_RDONLY
   O_WRONLY
   O_RDWR

6. O_CREAT
   → 없으면 생성

7. O_CREAT | O_EXCL
   → 이미 존재하면 실패

8. mode
   → O_CREAT로 새 파일 생성 시 permission 지정

9. S_IRUSR | S_IWUSR
   → 0600
   → Owner rw

10. read()
    > 0 : 읽은 byte 수
    = 0 : EOF
    = -1 : Error

11. Virtual Address
       ↓
      MMU
       ↓
    Page Table
       ↓
    Physical Address

12. Context Switch 시
    Page Table 전체가 MMU에 복사되는 것이 아니라
    현재 주소 공간을 가리키는 page-table 관련 register가 변경됨
```

특히 <strong>`S_IRUSR`</strong><strong>,</strong> <strong>`S_IWUSR`</strong><strong>,</strong> **`S_IRWXU`** <strong>같은 permission macro 조합은 교수님이 시험 문제 가능성을 직접 언급했으므로</strong> <strong>`📝 시험`</strong>**으로 따로 표시해 두는 게 좋다.**

## 고수준 파일 입출력

고수준 파일 입출력은 **표준 I/O 라이브러리(stdio)** 를 이용한다.

```text
Application
   ↓
stdio library
(fopen, fread, fwrite...)
   ↓
내부 buffer
   ↓
저수준 I/O / system call
   ↓
Kernel
```

파일 접근에는 정수형 FD 대신:

```text
FILE *fp;
```

형태의 **파일 스트림(File Stream)** 을 사용한다.

대표 함수:

```text
fopen()
fclose()
fread()
fwrite()
```

<a id="notion-3e21d46c18fc80298f5cd85a43bee9db"></a>

### 내부 버퍼 사용

고수준 I/O는 내부 buffer를 사용한다.

쓰기:

```text
fwrite()
  ↓
stdio 내부 buffer에 저장
  ↓
buffer가 차거나
fflush(), fclose() 등 발생
  ↓
실제 파일에 기록
```

읽기:

```text
fread()
  ↓
필요한 데이터 주변을 한 번에 읽어
stdio 내부 buffer에 저장
  ↓
프로그램에는 필요한 만큼 전달
```

즉, 저수준 I/O보다 system call 횟수를 줄여 효율적으로 동작할 수 있다.

---

<a id="notion-3e21d46c18fc802bb16ef425b65c44e2"></a>

## 저수준 vs 고수준 I/O

| 구분 | 저수준 I/O | 고수준 I/O |
| --- | --- | --- |
| 접근 방식 | System Call 중심 | stdio Library |
| 파일 식별 | `int fd` | `FILE *` |
| 대표 함수 | `open`, `read`, `write`, `close` | `fopen`, `fread`, `fwrite`, `fclose` |
| Buffer | 직접 관리 | 내부 buffer 사용 |
| 제어 | 세밀함 | 사용하기 편함 |

# 고수준 파일 입출력 함수

<a id="notion-3e21d46c18fc80f1b819ec540559e8aa"></a>

## `fopen()`

```text
FILE *fopen(const char *path, const char *mode);
```

파일을 열고 `FILE *` 스트림을 반환한다.

```text
path → 파일 경로
mode → 파일 열기 방식
```

대표 mode:

```text
"r"  → 읽기
"w"  → 쓰기, 없으면 생성 / 있으면 내용 삭제 후 새로 작성
"a"  → 파일 끝에 추가
"r+" → 읽기 + 쓰기
"w+" → 읽기 + 쓰기, 기존 내용 삭제
```

성공:

```text
FILE * 반환
```

실패:

```text
NULL 반환
```

---

<a id="notion-3e21d46c18fc805eb555c560757f9b53"></a>

## `fclose()`

```text
int fclose(FILE *stream);
```

파일 스트림을 닫는다.

```text
stream → 닫을 FILE *
```

성공:

```text
0
```

실패:

```text
EOF
```

`fclose()` 시 내부 output buffer에 남아 있던 데이터도 실제 파일에 반영된다.

---

<a id="notion-3e21d46c18fc800abce5e60cfb7711ce"></a>

## `fread()`

```text
size_t fread(
    void *ptr,
    size_t size,
    size_t nmemb,
    FILE *stream
);
```

파일에서 데이터를 읽는다.

```text
ptr    → 읽은 데이터를 저장할 buffer
size   → 데이터 1개 크기
nmemb  → 읽을 데이터 개수
stream → 입력 파일 스트림
```

예:

```text
fread(buf, 1, 4096, fp);
```

→ 최대 `4096`개의 1-byte 요소를 읽는다.

반환값:

```text
실제로 읽은 "요소 개수"
```

즉 `size = 1`이면 반환값이 실제 읽은 byte 수와 같다.

---

<a id="notion-3e21d46c18fc80e18dffe1b78306387f"></a>

## `fwrite()`

```text
size_t fwrite(
    const void *ptr,
    size_t size,
    size_t nmemb,
    FILE *stream
);
```

buffer의 데이터를 파일에 쓴다.

```text
ptr    → 쓸 데이터
size   → 데이터 1개 크기
nmemb  → 쓸 데이터 개수
stream → 출력 파일 스트림
```

예:

```text
fwrite(buf, 1, 100, fp);
```

→ `100 byte` 쓰기 요청.

반환값:

```text
실제로 쓴 "요소 개수"
```

---

<a id="notion-3e21d46c18fc80ed822cdc9da5b76286"></a>

# `size_t` vs `ssize_t`

저수준 I/O:

```text
ssize_t read(...);
ssize_t write(...);
```

고수준 I/O:

```text
size_t fread(...);
size_t fwrite(...);
```

차이:

```text
size_t
→ unsigned 정수형
→ 0 이상의 크기 표현

ssize_t
→ signed 정수형
→ 음수 표현 가능
```

그래서 `read()` / `write()`는:

```text
-1 → Error
```

를 직접 반환할 수 있다.

반면 `fread()` / `fwrite()`는 `size_t`이므로 음수를 반환하지 않는다.

```text
fread() < 요청 개수
```

인 경우:

```text
feof()
ferror()
```

등으로 EOF인지 error인지 확인해야 한다.

# `cpfile_block2.c`

고수준 파일 입출력을 이용한 **block 단위 파일 복사 예제**이다.

<a id="notion-3e21d46c18fc80429ae0c7c55ac9df1e"></a>

### 파일 열기

```text
src_fp = fopen(src_name, "r");
```

```text

dst_fp → 쓰기용
```

---

<a id="notion-3e21d46c18fc80c3a440cf58d55d17e8"></a>

### Block 단위 읽기

```text
uret1 = fread(buf, 1, block_size, src_fp);
```

최대 `block_size` byte를 읽는다.

```text
uret1 < block_size
```

이면 EOF 또는 error 가능성이 있으므로:

```text

```

로 EOF 여부를 확인한다.

<a id="notion-3e21d46c18fc80a9a44ce3ad0e6f8e21"></a>

```text
uret2 = fwrite(buf, 1, uret1, dst_fp);
```

실제로 읽은 `uret1` byte만큼 기록한다.

```text
fread()
  ↓
buf
  ↓
fwrite()
```

복사가 끝나면:

```text
fclose(src_fp);
fclose(dst_fp);
```

로 파일 스트림을 닫는다.

# 프로세스

<a id="notion-3e21d46c18fc80218eb8e6c588102ee8"></a>

## 1\. 프로세스(Process)

- <strong>프로그램(Program)</strong>: 디스크에 저장된 실행 가능한 파일
- <strong>프로세스(Process)</strong>: 프로그램이 메모리에 올라와 **실행 중인 상태**

Linux는 멀티태스킹 OS이므로 여러 프로세스가 동시에 실행될 수 있다.

각 프로세스는 식별을 위해 다음 값을 가진다.

```text
PID  : Process ID
PPID : Parent Process ID
```

<a id="notion-3e21d46c18fc80a89e19c0bf215b2f05"></a>

### ⚠️ PID 0

`PID 0 = 커널`이라고 단순히 표현하기보다는 다음처럼 이해하는 것이 정확하다.

> PID 0은 일반 user process가 아니라 **커널의 idle/swapper task**이다.

일반적으로 최초의 userspace process는:

```text
PID 1 → init/systemd
```

이다.

---

<a id="notion-3e21d46c18fc80c491b4f254267309a9"></a>

# 2\. 가상 메모리와 물리 메모리

프로세스가 사용하는 주소는 기본적으로 **가상 주소(Virtual Address)** 이다.

```text
CPU
 │ Virtual Address
 ▼
MMU
 │ Page Table 참조
 ▼
Physical Address
 │
 ▼
Physical Memory / MMIO
```

MMU는 **가상 주소 → 물리 주소** 변환을 수행한다.

가상 메모리 구조, 페이지 크기, page table 구조 등은 CPU architecture와 시스템 구성에 따라 달라질 수 있다.

---

<a id="notion-3e21d46c18fc80658a1ff5e822e27c4b"></a>

## 페이지 테이블

프로세스마다 독립적인 가상 주소 공간과 이를 위한 page table 정보가 존재한다.

```text
Process 1 → Page Table 1
Process 2 → Page Table 2
Process 5 → Page Table 5
```

CPU가 실행할 프로세스를 바꾸는 **Context Switch**가 발생하면 현재 프로세스의 page table을 참조하도록 관련 register가 변경된다.

<a id="notion-3e21d46c18fc8037ad6ae65e423048fc"></a>

### ⚠️ 표현 수정

```text
페이지 테이블을 MMU에 로딩한다
```

보다는:

> **현재 프로세스의 page table을 가리키도록 CPU의 page-table 관련 register를 변경한다.**

라고 이해하는 것이 정확하다.

MMU는 그 page table을 참조하여 주소 변환을 수행하고, 자주 사용하는 변환 결과는 **TLB**에 cache한다.

# 3\. 프로세스의 User Space 정보

Linux의 `/proc` 파일 시스템을 통해 프로세스 정보를 확인할 수 있다.

```text
cat /proc/PID/maps
```

예:

```text
cat /proc/1234/maps
```

`/proc/PID/maps`는 해당 프로세스의 **가상 메모리 매핑 정보**를 보여준다.

예를 들어:

```text
CODE
읽기 전용 영역
Data
Heap
Shared Library
Stack
mmap 영역
```

등의 주소 범위와 접근 권한을 확인할 수 있다.

# 4\. 프로세스 주소 공간

각 프로세스는 자신만의 **Virtual Address Space**를 가진다.

프로세스 입장에서는 전체 가상 주소 공간을 자신이 독립적으로 사용하는 것처럼 보인다.

```text
Process A              Process B

Virtual Address        Virtual Address
┌──────────────┐       ┌──────────────┐
│ Kernel Space │       │ Kernel Space │
├──────────────┤       ├──────────────┤
│ User Space   │       │ User Space   │
└──────────────┘       └──────────────┘
```

- **User Space**: 프로세스마다 독립적
- **Kernel Space**: 논리적으로 각 주소 공간에 존재하지만, 일반적으로 동일한 kernel 영역을 공통으로 mapping하여 사용

즉:

> 각 프로세스의 **user 영역은 분리**되어 있지만, **kernel 영역은 공통 kernel을 접근하기 위한 mapping을 공유**한다.

---

<a id="notion-3e21d46c18fc8068a8d6c897d3af81cc"></a>

## Segment

프로그램의 메모리 영역은 용도와 권한에 따라 여러 영역으로 나뉜다.

대표적으로:

```text
Text(Code) → 실행 코드
RO         → 읽기 전용 데이터
Data       → 초기화된 전역/정적 변수
BSS        → 초기화되지 않은 전역/정적 변수
Heap       → 동적 메모리
Stack      → 지역 변수, 함수 호출 정보
```

이러한 영역들을 흔히 **segment**라고 부른다.

<a id="notion-3e21d46c18fc80d3933bebf91a583a15"></a>

# 5\. 프로세스 상태 확인

명령어:

```text
ps ax
```

> `px ax` ❌
>
> `ps ax` ✅

`STAT` 항목에서 process 상태를 확인할 수 있다.

| STAT | 의미 |
| --- | --- |
| `R` | Running / Runnable |
| `S` | Interruptible Sleep |
| `D` | Uninterruptible Sleep |
| `T` | Stopped / Traced |
| `Z` | Zombie |

<a id="notion-3e21d46c18fc80b39e41dabdeaf2360a"></a>

### 간단히 이해

```text
R → 실행 중 또는 CPU 실행 대기
S → sleep 상태, signal 등에 의해 깨어날 수 있음
D → 주로 I/O 등을 기다리는 sleep, 일반 signal로 쉽게 깨지지 않음
T → 실행 중지됨
Z → 종료됐지만 부모가 종료 상태를 아직 회수하지 않음
```

이 상태 값들은 Linux kernel 내부의 **task 상태**와 관련되어 있다.

## 핵심 복습

```text
Program = 디스크에 존재하는 실행 파일
Process = 실행 중인 프로그램

PID  = 프로세스 ID
PPID = 부모 프로세스 ID

Process마다
→ 독립적인 User Virtual Address Space
→ Page Table 정보 존재

CPU Virtual Address
        ↓
       MMU
        ↓
   Page Table 참조
        ↓
Physical Address

/proc/PID/maps
→ 프로세스의 가상 메모리 매핑 확인

ps ax
→ 프로세스 및 상태 확인
```

특히 **“page table 전체를 MMU에 로딩한다”가 아니라, context switch 시 현재 프로세스의 page table을 가리키는 설정이 변경된다**는 부분은 원래 필기에서 수정해서 기억하는 게 좋다.

# 프로세스 생성/실행 관련 함수 정리

<a id="notion-3e21d46c18fc80de9a90d9c6dfa67222"></a>

## 1\. `system()`

```text
int system(const char *command);
```

Shell을 통해 명령을 실행하고, **명령이 끝날 때까지 기다린 뒤 종료 상태를 반환**한다.

개념적으로:

```text
system(command)
    ↓
/bin/sh -c command
    ↓
명령 실행
    ↓
종료까지 대기
    ↓
종료 상태 반환
```

따라서 shell 문법을 사용할 수 있다.

```text
system("ls /etc | grep init > init.txt");
```

- `|` pipe 사용 가능
- `>` redirection 사용 가능
- 따라서 **정상적으로 동작**

<a id="notion-3e21d46c18fc8079ac2af2c6a7380f31"></a>

### 📝 시험 포인트

```text
system("ls /etc | grep init > init.txt");
```

→ `/bin/sh -c`로 실행되므로 **동작한다.**

---

<a id="notion-3e21d46c18fc80129a12d99466cdeec0"></a>

# 2\. 프로세스 종료 상태

프로세스가 **어떻게 종료되었는지** 나타내는 값이다.

대표적으로:

```text
정상 종료
→ exit code가 의미 있음

Signal에 의한 종료
→ signal 번호가 의미 있음
```

실제 코드에서는 직접 비트를 해석하기보다 다음 macro를 사용한다.

```text
WIFEXITED(status)     // 정상 종료 여부
WEXITSTATUS(status)   // exit code

WIFSIGNALED(status)   // signal 종료 여부
WTERMSIG(status)      // 종료시킨 signal 번호
```

<a id="notion-3e21d46c18fc8005a6d8e284595bc427"></a>

### 📝 시험 포인트 — status 계산

수업에서 다루는 형태:

```text
status = 0x0000
→ exit code = 0

status = 0x0200
→ exit code = 2

status = 0x0800
→ exit code = 8

status = 0x0001
→ signal 1에 의해 종료
```

예:

```text
return 8;
```

이라면 부모가 받은 종료 상태는 일반적으로:

```text
0x0800
```

이고:

```text
WEXITSTATUS(status)
```

결과는:

```text
8
```

<a id="notion-3e21d46c18fc803e8942e93a757d3f99"></a>

### ⚠️ 중요

`WEXITSTATUS()`는 아무 status에나 쓰는 게 아니라:

```text
if (WIFEXITED(status))
    WEXITSTATUS(status);
```

처럼 **정상 종료인지 확인한 뒤 사용하는 것이 정확하다.**

---

<a id="notion-3e21d46c18fc80e0b177ca2ffa2e7af6"></a>

## `system()`의 종료 상태

```text
ret = system("ls -l");
```

shell이 command를 정상적으로 실행했다면 **실행된 command의 종료 결과가 반영**된다.

<a id="notion-3e21d46c18fc80509714f9d0c0773114"></a>

### ⚠️ 중요 / 시험

```text
/bin/sh가 command를 실행
→ command의 exit code가 system() 결과에 반영됨
```

명령을 찾을 수 없는 경우 shell은 일반적으로:

```text
exit code = 127 = 0x7f
```

를 반환한다.

예:

```text
ret = system("wrong_command");
```

```text
WEXITSTATUS(ret)
```

→ 일반적으로 `127`

# 3\. `exec()` 계열

`exec()`는 새로운 프로세스를 추가로 만드는 것이 아니라:

> **현재 프로세스의 실행 이미지를 새로운 프로그램으로 교체한다.**

```text
현재 Process
PID = 100
Program A
     ↓ exec()
PID = 100
Program B
```

PID는 그대로 유지된다.

---

<a id="notion-3e21d46c18fc80e99562f9263af10dfd"></a>

## `execl()`

```text
execl(path, arg0, arg1, ..., NULL);
```

예:

```text
execl("/bin/ls", "ls", "-l", NULL);
```

<a id="notion-3e21d46c18fc809ab7a5eee587702c7d"></a>

### 📝 시험 포인트

argument의 마지막은 반드시:

```text
NULL
```

로 끝나야 한다.

---

<a id="notion-3e21d46c18fc80ea8220c7d6d4c7dd88"></a>

## `execl()` 성공 시 이후 코드가 실행되지 않는 이유

```text
ret = execl("/bin/ls", "ls", "-l", NULL);

printf("hello");
```

`exec()`가 성공하면 현재 프로그램 자체가 `/bin/ls`로 **교체**된다.

따라서 기존 프로그램의:

```text
printf("hello");
```

까지 돌아오지 않는다.

```text
exec 성공
→ 반환하지 않음

exec 실패
→ -1 반환
→ 이후 코드 실행
```

---

<a id="notion-3e21d46c18fc804c8459fcc9dc67cb88"></a>

# 4\. `execl()` vs `execlp()`

<a id="notion-3e21d46c18fc80489aedcd9d44ff480c"></a>

### `execl()`

경로를 직접 사용한다.

```text
execl("/bin/ls", "ls", "-l", NULL);
```

→ 성공

```text
execl("ls", "ls", "-l", NULL);
```

→ 현재 위치에 `ls`가 없다면 실패

<a id="notion-3e21d46c18fc80dda881c463617fb669"></a>

### `execlp()`

`PATH` 환경변수에서 프로그램을 검색한다.

```text
execlp("ls", "ls", "-l", NULL);
```

→ `PATH`에서 `ls`를 찾아 실행

| 함수 | 특징 |
| --- | --- |
| `execl()` | 지정된 경로 사용 |
| `execlp()` | `PATH`에서 검색 |

---

<a id="notion-3e21d46c18fc80288897e7aef7b6247d"></a>

## `argv[0]`

```text
execl("/bin/ls", "xxx", "-l", NULL);
```

실행 프로그램은 `/bin/ls`지만 새 프로그램 입장에서는:

```text
argv[0] = "xxx"
```

가 된다.

일반적인 프로그램은 큰 영향을 받지 않을 수 있지만, <strong>BusyBox처럼</strong> <strong>`argv[0]`</strong>**에 따라 동작을 변경하는 프로그램도 있다.**

---

<a id="notion-3e21d46c18fc80c599a8f1cf53d28c8d"></a>

# 5\. `fork()`

```text
pid_t fork(void);
```

현재 프로세스를 기반으로 **자식 프로세스를 생성**한다.

```text
fork 이전
→ Parent 1개

fork 이후
→ Parent + Child
```

부모와 자식은 `fork()` 다음 코드부터 각각 실행한다.

---

<a id="notion-3e21d46c18fc802eb998dc77d98c2caf"></a>

## `fork()` 반환값

<a id="notion-3e21d46c18fc80a3b73efba14f73d2a0"></a>

### 📝 반드시 암기

```text
-1 → fork 실패

 0 → 자식 프로세스

>0 → 부모 프로세스
     값은 생성된 자식의 PID
```

예:

```text
부모 PID = 32686
자식 PID = 32687
```

이면:

```text
Parent
pid_temp = 32687

Child
pid_temp = 0
```

자식이 자신의 PID를 알고 싶으면:

```text
getpid();
```

를 사용한다.

---

<a id="notion-3e21d46c18fc8019953df649364c5128"></a>

# 6\. `fork()` 후 변수

`fork()` 직전:

```text
pid = 32686
msg = "none"
```

fork 후 처음에는:

```text
Parent                Child

pid = 32686           pid = 32686
msg = "none"          msg = "none"

pid_temp = 32687      pid_temp = 0
```

자식 코드:

```text
pid = getpid();
msg = "this is child";
```

결과:

```text
Child
pid = 32687
msg = "this is child"
```

부모:

```text
msg = "this is parent";
```

결과:

```text
Parent
pid = 32686
msg = "this is parent"
```

---

<a id="notion-3e21d46c18fc80638393e8c099f27b9a"></a>

## 부모/자식은 변수를 공유하지 않음

`fork()` 이후 부모와 자식은 **독립적인 가상 주소 공간**을 가진다.

```text
Parent의 msg
≠
Child의 msg
```

한쪽에서 값을 변경해도 다른 쪽 변수에는 영향을 주지 않는다.

실제로 Linux는 성능을 위해 **Copy-On-Write(COW)** 를 사용하지만, 프로그래머 관점에서는 독립적인 변수라고 생각하면 된다.

---

<a id="notion-3e21d46c18fc80f49067c98d3999fbb3"></a>

# 7\. 부모/자식 실행 순서

`sleep()`이 없다면:

```text
fork()
   ├─ Parent
   └─ Child
```

둘은 독립적으로 scheduler의 스케줄링을 받는다.

따라서:

```text
Parent가 먼저 실행될 수도 있고
Child가 먼저 실행될 수도 있음
```

순서는 보장되지 않는다.

예제에서는:

```text
Child  → sleep(3);
Parent → sleep(5);
```

이므로 자식이 먼저 깨어나 출력한 것이다.

# 8\. `wait()`

```text
pid_t wait(int *status);
```

부모가 **자식 중 하나가 종료될 때까지 기다린다.**

```text
Parent
  │
 wait()
  │
  │ 대기
  │
Child 종료
  ↓
Parent 다시 실행
```

반환값:

```text
성공 → 종료된 자식 PID
실패 → -1
```

---

<a id="notion-3e21d46c18fc800eb3a1e4118ce6806a"></a>

## 📝 중요

자식의 종료 상태가 필요 없다면:

```text
wait(NULL);
```

처럼 사용 가능하다.

```text
status 필요 없음
→ NULL
```

---

<a id="notion-3e21d46c18fc8013aae8c7fd35549995"></a>

# 9\. `waitpid()`

```text
pid_t waitpid(pid_t pid, int *status, int options);
```

`wait()`와 달리 **어떤 자식을 기다릴지 지정할 수 있다.**

예:

```text
waitpid(pid_temp, &status, 0);
```

→ `pid_temp` 자식이 종료될 때까지 기다림.

```text
wait()
→ 자식 중 하나

waitpid()
→ 특정 자식을 지정 가능
```

---

<a id="notion-3e21d46c18fc8013be67c43969f81b04"></a>

# 10\. `WNOHANG`

```text
waitpid(pid_temp, &status, WNOHANG);
```

<a id="notion-3e21d46c18fc80f48782d9a5dca958e6"></a>

### 📝 중요

자식이 아직 종료되지 않았더라도 **기다리지 않고 즉시 반환**한다.

즉 Non-blocking 방식이다.

반환값:

```text
> 0
→ 종료된 자식 PID

0
→ 자식이 아직 종료되지 않음

-1
→ Error
```

따라서:

```text
pid_wait = waitpid(pid_temp, &status, WNOHANG);
```

에서:

```text
pid_wait == 0
```

이면:

> 자식은 아직 실행 중이다.

---

<a id="notion-3e21d46c18fc8050be54d92d0b10459e"></a>

## 예제의 반복문

```text
for (;;)
{
    pid_wait = waitpid(pid_temp, &status, WNOHANG);

    if (pid_wait)
        break;
}
```

자식이 `sleep(3)` 중이라면 부모는:

```text
waitpid()
waitpid()
waitpid()
waitpid()
...
```

를 계속 호출한다.

이를 **Busy Waiting**이라고 한다.

CPU를 계속 사용하기 때문에 효율적이지 않다.

실제 코드에서는 polling이 필요하다면 보통 중간에 sleep 등을 넣는다.

```text
while ((pid_wait = waitpid(pid_temp, &status, WNOHANG)) == 0)
{
    sleep(1);
}
```

# 전체 흐름

Linux에서 자식 프로그램을 실행하는 대표적인 구조는:

```text
Parent
   │
 fork()
   │
   ├───────────────┐
   │               │
Parent            Child
   │               │
wait()            exec()
   │               │
자식 대기         다른 프로그램 실행
   │               │
   └──── 종료 ◀────┘
```

즉:

```text
fork()
→ 자식 생성

exec()
→ 자식을 새로운 프로그램으로 교체

wait()/waitpid()
→ 부모가 자식 종료를 회수
```

---

<a id="notion-3e21d46c18fc80dc8abfcc25e72980cb"></a>

# 📝 시험 직전 체크

```text
system()
→ /bin/sh -c
→ shell 기능 사용 가능
→ 명령 종료까지 기다림
```

```text
exec()
→ 현재 프로세스의 실행 이미지 교체
→ PID 유지
→ 성공하면 돌아오지 않음
→ execl() argument 마지막 NULL
```

```text
fork()

-1 → 실패
 0 → 자식
>0 → 부모, 자식 PID
```

```text
fork 후
→ 부모/자식 독립 실행
→ 변수 공유 X
→ 실행 순서 보장 X
```

```text
wait(NULL)
→ 종료 상태 필요 없음

wait()
→ 자식 중 하나 대기

waitpid()
→ 특정 자식 지정 가능

WNOHANG
→ 기다리지 않고 즉시 반환
```

```text
정상 종료
→ WIFEXITED()
→ WEXITSTATUS()

Signal 종료
→ WIFSIGNALED()
→ WTERMSIG()
```

특히 시험에서는 **`fork()`** <strong>이후 프로세스 개수·변수 값·</strong><strong>`fork()`</strong> <strong>반환값을 각각 가지치기해서 추적하는 문제</strong>와 <strong>자식의</strong> <strong>`return N`</strong><strong>을 보고 부모의</strong> **`status`** <strong>값을 계산하는 문제</strong>를 중점적으로 대비하면 된다.
